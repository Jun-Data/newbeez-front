## 1. 익명 댓글 (2차)

**결과별 스레드.** 이상형 월드컵 방식으로, **같은 팀이 나온 사람들끼리 모인다.** 답코드가 달라도 팀이 같으면 한 방이다.

```sql
CREATE TABLE comments (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  category_slug VARCHAR(32)  NOT NULL,   -- 'football' (선반영)
  result_slug   VARCHAR(32)  NOT NULL,   -- 결과별 스레드
  nickname      VARCHAR(20)  NOT NULL,
  password      VARCHAR(60)  NOT NULL,   -- BCrypt 해시
  content       VARCHAR(300) NOT NULL,
  created_at    DATETIME     NOT NULL,
  deleted       BOOLEAN      DEFAULT FALSE,
  INDEX idx_thread (result_slug, created_at DESC)
);
```

| 메서드 | 경로 | 비고 |
|---|---|---|
| GET | `/api/v1/comments?resultSlug=` | 페이지네이션 |
| POST | `/api/v1/comments` | `resultSlug` 포함 |
| POST | `/api/v1/comments/{id}/delete` | 비밀번호를 **body**로 |

- **삭제가 `DELETE ...?password=xxx` 면 안 된다** — 비밀번호가 서버 접근 로그에 남는다
- **익명 + 공개 = 스팸·욕설 무방비.** 최소한 IP 기준 rate limit(분당 3건) + 길이 제한
- 물리 삭제 대신 `deleted` 플래그 → 사고 시 복구 가능
- 렌더링은 **CSR**. 결과 페이지는 ISR 정적이고 백엔드가 죽어도 결과 카드는 떠야 한다

> **왜 MVP 맨 마지막인가**: 스레드가 15개로 쪼개져서, 사용자가 적을 때 열면 **전부 빈 방**이 된다.

## 2. `/football` 입문 허브 (2차)

> **퀴즈는 입구고 카테고리 허브가 본체다.** 서비스 정체성은 "입문의 정석" — 뭘 골라야 할지 막막한 뉴비를 위한 가이드이며, 퀴즈는 그 안의 도구 하나다.

**MVP 동안 `/football` 은 히어로 + 퀴즈 버튼만 있는 얇은 안내 페이지로 둔다.** 핵심 동선(인트로 → 퀴즈 → 결과 → 공유)에 허브가 없기 때문 — 공유 링크를 타고 온 사용자는 허브를 지나가지 않는다.

| 섹션 | 내용 | 데이터 |
|---|---|---|
| 히어로 + 퀴즈 시작 버튼 | | 없음 |
| **입문 꿀팁** | 뉴비가 카테고리를 이해하는 정보 — 축구 규칙, 리그별 설명, 용어 | 우리가 쓴 글 |
| **퀴즈 결과 팀 순위** | 퀴즈로 많이 나온 팀 | `participant_logs` 집계 |
| **입문팀 추천 순위** | 사람들이 뉴비에게 권하는 팀 (§3) | UGC |
| 커뮤니티 게시판 | | UGC |

**팀 순위가 둘이라는 점에 주의.** 하나는 *알고리즘이 준 답*, 하나는 *사람들의 추천*이라 성격이 다르다. 라벨을 확실히 구분해야 하며, 둘이 어긋나는 것 자체가 콘텐츠가 된다.

**팀 순위는 추가 스키마가 필요 없다:**

```sql
SELECT result_slug, COUNT(*) AS cnt
FROM participant_logs WHERE category_slug = 'football'
GROUP BY result_slug ORDER BY cnt DESC;
```

사용자별로 다르지 않은 **15행**이라 캐시가 완벽히 먹는다. → `GET /api/v1/participants/ranking` (1분 캐시)

**미루는 이유 — 닭과 달걀**: 순위·추천·게시판 모두 사용자가 있어야 의미가 있다. 오픈 첫날 "참여자 3명 · 게시글 0개"는 사회적 증거가 아니라 **버려진 서비스**로 읽힌다.

> **결과 화면에는 비율(%)을 넣지 않는다** (2026-08-11 결정). 1위 팀은 참여자의 20% 이상이라 "23%가 같은 결과"는 **최대 집단에게 "너 흔해"로 읽힌다.** 순위는 허브에서만 보여주고, 결과 → 허브 링크(`다른 사람들은 어떤 팀이 나왔을까?`)로 동선을 잇는다.

## 3. 입문팀 UGC + 인증 (3차)

**나무위키형.** 운영자가 후보를 띄우고 투표받는 방식이 **아니라**, 사용자가 등록하고 다른 사용자가 인정해 순위가 만들어진다. 우리가 큐레이션하면 블로그지만 사용자가 만들면 커뮤니티 자산이 되고, 이게 복제하기 어려운 해자가 된다.

**"입문템" = 그 취미를 시작할 때 처음 고르는 것.** 물건에 한정되지 않는다 — 러닝=러닝화(제품) · 애니=입문작(콘텐츠) · 등산=초보 코스(장소) · **축구=입문팀**.

**축구는 우리 15팀으로 한정한다** (2026-08-11 결정). 나폴리·아약스 등 외부 팀은 받지 않는다. 그러면 `team_results` 를 그대로 재사용할 수 있고, 등록 행위가 "새 항목 생성"이 아니라 **"15개 중 고르기 + 추천 이유 쓰기"**가 되어 아래 위험 #1이 원천 차단된다.

### 열기 전에 해결할 것

| # | 위험 | 대응 |
|---|---|---|
| 1 | **중복 등록** — "나이키 페가수스"/"페가수스 41"이 따로 쌓여 순위가 무의미해짐. UGC 랭킹의 1번 실패 모드 | 유사 항목 제안 + `merged_into` 병합·추천수 합산 |
| 2 | **스팸·광고** — 익명 등록은 자기 상품 홍보로 이어짐 (러닝화·카메라가 특히) | 로그인 필수 + 최소 설명 길이 + 신고 |
| 3 | **어뷰징** — 자기 등록물 자추 | 로그인 + `UNIQUE(item_id, user_id)` |
| 4 | **콜드 스타트 역설** — "사용자가 만든다"와 "처음부터 비어 있다"는 다르다. **빈 화면에는 아무도 첫 번째로 쓰지 않는다** | 우리가 5~10개 **마중물**을 등록하되 창구는 열어둠 |

### 인증 — 카카오 소셜 로그인

**자체 회원가입을 하지 않는다.** 이메일을 받아도 우리가 할 일이 없는데(메일 발송·마케팅 안 함) 비밀번호 보관 책임·재설정 흐름만 떠안는다.

**문턱은 필요한 곳에만.** 로그인을 전부에 걸면 서비스가 죽는다.

| 행동 | 로그인 |
|---|---|
| 퀴즈 풀기 · 결과 보기 · 공유 | **절대 요구 안 함** |
| 댓글 쓰기 | 익명 + 비밀번호 유지 |
| **입문팀 등록·추천** | **필수** — 순위의 신뢰가 이 기능의 존재 이유. 못 믿을 순위는 없느니만 못하다 |

**도입 시점 = 입문팀을 열 때.** 인증이 필요한 유일한 기능이 이것뿐이라, 지금 넣으면 MVP만 밀린다.

> ⚠️ CLAUDE.md 의 "무거운 인프라(인증)는 명시적 요청 전엔 도입하지 않음" 조항 — 2026-08-11 사용자가 명시적으로 요청하여 이 단계에 한해 해제.

### 스키마 방향 (확정 아님)

```sql
items (
  id, category_slug, name, summary, recommend_reason,
  image_path, external_url, extra JSON,   -- 카테고리별 고유 속성
  status,          -- ACTIVE | MERGED | HIDDEN
  merged_into, endorse_count, created_by, created_at
)
item_endorsements (item_id, user_id, created_at, UNIQUE(item_id, user_id))
users (id, provider, provider_uid, nickname, created_at)
```

**카테고리별 테이블(`running_shoes`, `cameras`…)로 나누지 않는다.** 카테고리를 늘리는 게 서비스의 목표인데 그 방식은 카테고리마다 테이블·엔티티·API가 필요해 **확장 비용이 가장 비싸다.** 공통 컬럼 + `extra JSON` 으로 흡수하고, 순위·추천은 공통 컬럼만 쓰므로 JSON 내부를 쿼리할 일이 거의 없다.

> **축구만 예외**로 `team_results` 재사용. 15팀 한정이 주는 안전함을 취한다.

## 4. 백엔드 호스팅 (조사 완료 · 결정 보류)

MVP는 백엔드 없이 완결되므로 지금 확정할 필요가 없다. 다만 **A1 인스턴스 확보가 복불복**(수시간~수일 실패)이라 필요해진 뒤 시작하면 그때 막힌다 → **미리 시도해둘 것.**

**1순위: Oracle Cloud Always Free (서울)** — A1 2 OCPU/12GB + MySQL HeatWave Always Free 50GB

「무료 + 서울 리전 + 진짜 MySQL + 콜드스타트 0 + **자동 과금 없음** + 기한 없음」 6가지를 동시에 만족하는 유일한 후보. 한도를 넘으면 과금이 아니라 **생성 차단·정지**로 동작한다. 상용화 전환도 콘솔에서 PAYG 버튼 하나 — 인스턴스·DB·IP 그대로라 **마이그레이션 0**.

- 대가: 배포 난이도 HARD(SSH·systemd·nginx 직접 운영) · A1 확보 복불복 · **홈 리전은 가입 시 1회 확정이라 반드시 서울 선택**
- ⚠️ 2026-06-15에 4 OCPU/24GB → **2 OCPU/12GB로 축소**됨. 온라인 가이드 대부분이 옛 수치니 그대로 따라 하지 말 것

**2순위: Cloud Run(서울) + TiDB Cloud Starter(도쿄)** — A1을 못 잡거나 "git push 배포"가 더 중요할 때. 단 콜드스타트 5~15초, 지출 하드 상한 없음(`--max-instances` 필수), TiDB는 MySQL **호환**이라 트리거·프로시저 금지.

**피할 것**: Render(**MySQL 없음** · 무료 DB 30일 만료) · AWS Free plan(**6개월 뒤 계정 폐쇄**) · Railway(무료 월 $1 = 4~6일치) · Fly.io·PlanetScale·Koyeb(무료 폐지/차단) · Gabia·Cafe24(**JDK 21 미지원** / JVM 256MB)

**락인 방어 — 어디를 고르든 지금부터 적용**: Dockerfile 컨테이너화 · DB 접속은 환경변수로만 · Flyway로 스키마 코드화 · **트리거·프로시저·벤더 함수 금지.** 가장 아픈 락인은 Postgres로 넘어가는 것(DDL·SQL·JPA 방언 전면 재작업).

## 5. 다른 카테고리 (4차)

러닝 · 카메라 · 등산 · 영화 · 애니메이션 …

**축구 하나만 만들되 구조는 미리 잡아뒀다** — URL 계층 `/<category>/...` 와 DB `category_slug` 컬럼. 컬럼 하나면 **마이그레이션 없이 행 추가만으로** 새 카테고리를 연다.

카테고리마다 퀴즈 문항·좌표가 다르므로 `lib/` 도 카테고리별로 나뉜다. Next의 라우트별 코드 분할이 적용되어 번들이 함께 커지지는 않는다.
