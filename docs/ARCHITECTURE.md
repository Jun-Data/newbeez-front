## 0. 서비스 컨셉 (오해 주의)

**재는 것은 사용자 본인의 성향, 내주는 것은 닮은 팀.**

사용자가 *감독으로 팀에 입단해* 문항에 답하는 연출을 쓰지만 **감독은 가벼운 스킨일 뿐 측정 대상이 아니다.** "당신은 이런 감독입니다"가 아니라 **"당신과 가장 닮은 팀은 ○○입니다"**가 결과다. MBTI식 단일 정체성 카드.

따라서 4축(전술·자원·조직·목표)도 "감독으로서의 전술 성향"이 아니라 **사용자 성향을 축구 언어로 옮긴 좌표**로 읽는다.

**'감독님' 호칭은 퀴즈 진행 화면 전용.** 랜딩·결과에서는 사용자를 그렇게 부르지 않으므로, 결과의 "감독 엔초 마레스카"는 자연스럽게 구단 감독으로 읽힌다 — 용어를 따로 분리할 필요 없음.

## 2. 역할 분담

**계산은 프론트, 표시 데이터는 백엔드.** 사용자 답을 백엔드로 보내 결과를 받아오는 구조가 **아니다.**

| 데이터 | 소유 | 이유 |
|---|---|---|
| 문항·선택지·배점 | 프론트 `lib/` | 답코드 URL 계약과 결박됨 → 앱과 함께 배포되어야 함 |
| 팀 좌표·리그·라이벌 | 프론트 `lib/clubs.ts` | 채점 입력. 네트워크 없이 즉시 계산 |
| 채점 로직 | 프론트 (순수함수) | 마지막 클릭 → 결과까지 왕복 0회. 전수 감사 가능 |
| 팀 표시 정보 (소개·인물·카피·유니폼 게시물 주소) | 백엔드 DB | 수동 큐레이션 + 시즌 갱신. **이미지 파일은 없다** (§4.7·§7.3) |
| 팀 컬러 | 프론트 `lib/team-display.ts` | 표시 전용. 백엔드가 죽어도 히어로·OG 가 살아야 한다 (§7.4) |
| 참여자 수 | 백엔드 DB | 실시간 집계 |

두 층을 잇는 계약은 **`slug`** (`man-city`, `chelsea` …). `lib/clubs.ts` 와 `team_results` 가 서로를 몰라도 slug 하나로 연결된다.

**감사 통과 상태**: 굶는 팀 0 · EPL 2.38배 · ETC 2.69배 · ALL 4.39배(균등 모델 기준) · 균등·중앙편향·극단편향 세 모델 모두 통과 · 답코드 왕복 196,608건.

### 3.1 답코드 규격

```
/football/result/man-city#a=032102223
                            │└──────┘
                            │   └──── Q2~Q9 성향 8자리 (각 0~3)
                            └──────── Q1 리그 1자리 (0=EPL · 1=ETC · 2=ALL)
```

- **9자리** = 리그 1 + 성향 8
- **Q1을 포함하는 이유** — Q1이 후보 팀 풀을 정하므로 **같은 성향 점수라도 리그가 다르면 다른 팀이 나온다.** 리그가 빠지면 `matchTeam` 을 재현할 수 없어 `slug` 대조 검증이 불가능하다
- **검증**: 클라이언트에서 답코드로 `matchTeam` 을 재실행해 경로의 `slug` 와 대조. 채점 함수가 프론트에 있으므로 **추가 비용 0**
- 파싱 실패·불일치 시 **그래프 영역만 생략**하고 팀 카드는 정상 렌더 (페이지가 깨지면 안 됨)
- ⚠️ **URL은 한번 공유되면 못 바꾸는 계약**
- 🔑 **`?a=`(쿼리) 가 아니라 `#a=`(해시) 다** (2026-10-20 변경 · 결과 화면 구현 전이라 비용 0). Instagram `embed.js` 는 결과 페이지의 **경로와 쿼리스트링을 iframe 주소(`rp=`)에 실어 Meta 로 보낸다** — 쿼리였다면 문항별 답 전체가 Meta 쿠키와 함께 넘어간다. 해시는 브라우저 밖으로 나가지 않는다(서버도 임베드도 받지 않음). 덤으로 서버 컴포넌트가 쿼리를 읽을 일이 없어져 정적 생성이 깨질 위험(§4.2)도 사라졌다. 근거는 [LEGAL.md §3](LEGAL.md)

### 3.2 ⚠️ 결과 화면 구현 시 반드시 처리할 것

`lib/scoring.ts` 는 **유효한 입력만 들어온다고 가정**한다. 조작된 URL이 그 가정을 깨뜨린다.

| 위치 | 무슨 일이 나나 |
|---|---|
| `matchTeam` — `ranked[0].cos` | 리그 자리가 잘못되면 `pool` 이 **빈 배열** → `undefined` 접근 → **페이지 전체가 죽는다** |
| `scoreAxes` — `ITEM_VALUES[q.slot][choices[q.id]]` | 답이 4 이상이면 `undefined` → **NaN 이 4축 전체로 전파** |

**→ `decodeAnswerCode` 가 `null` 을 뱉으면 `matchTeam` 을 아예 부르지 않는다.** 검증은 이미 `lib/answer-code.ts` 안에 있으므로, 화면은 `null` 여부만 확인하면 된다.

### 3.3 문항을 손댈 때의 규칙

| 변경 | 답코드 영향 | 대응 |
|---|---|---|
| 문항 **텍스트** 수정 | 없음 | 자유롭게 |
| 문항 **추가·삭제** | 자릿수가 바뀜 | 옛 링크는 `decode` 가 `null` → 그래프만 생략 |
| 문항 **순서** 변경 | 자리의 의미가 뒤바뀜 | 🚨 옛 링크가 다른 그래프를 그림 |
| 문항 **축·배점** 변경 | **자릿수는 그대로인데 의미만 달라짐** | 🚨 가장 위험 — 길이로도 못 걸러내고 에러도 안 남 |

**`scripts/audit-answer-code.ts` 가 이 사고를 막는다.** 계약(`EXPECTED_LEAGUES` · `EXPECTED_SCALE_IDS` · `EXPECTED_AXIS_SLOT`)을 하드코딩해 두고 `questions.ts` 와 대조하므로, 위 3·4번을 저지르면 `pnpm quiz:audit` 이 즉시 실패한다. **조용히 깨지는 것을 시끄럽게 깨지도록** 바꾸는 장치다.

> ⚠️ **왕복 전수 감사만으로는 못 잡는다.** 모든 조합을 도는 검사라 순서가 바뀌어도 왕복은 여전히 성공한다. 그래서 계약 대조가 따로 필요하다.

### 3.4 그래프는 4축 다이아몬드

축이 4개이므로 **사각형**. 오각형이 아니다. 5번째 축 추가는 기각됨(채점 엔진·감사 전면 재작업).

## 4. 프론트엔드 설계

### 4.1 라우팅

**3단 계층**: **홈 → 카테고리 → 테스트**. 다른 카테고리도 같은 모양으로 늘어난다.

⚠️ **`/football` 은 테스트가 아니라 카테고리 페이지다.** 테스트는 그 아래 `/football/quiz` 부터 시작하고, 테스트 층은 **인트로 → 진행 → 결과 세 화면**으로 이루어진다.

| 계층 | 경로 | 역할 | 렌더링 |
|---|---|---|---|
| **① 홈** | `/` | **Newbeez 홈** — 카테고리 목록. 🚫 **MVP 범위 밖** — 지금은 `/football/quiz` 로 리다이렉트 ([FUTURE §5](FUTURE.md)) | 정적 |
| **② 카테고리** | `/football` | 해외축구 — **MVP에선 히어로 + 퀴즈 버튼만** ([FUTURE §2](FUTURE.md)) | 정적 |
| **③ 테스트** | `/football/quiz` | **테스트 인트로** — 히어로·시작 버튼·참여자 수. **공유·유입의 착지점** | 정적 셸 + CSR |
| ↳ | `/football/quiz/play` | 퀴즈 진행 (Q1~Q9) | 클라이언트 단독 |
| ↳ | `/football/result/[slug]` | 결과 | ISR + CSR 오버레이 |

**인트로와 진행을 나누는 이유**: 인트로는 **공유되고 색인되는 페이지**라 OG 메타데이터·정적 생성 대상이고, 진행 화면은 클라이언트 상태 덩어리라 성격이 정반대다. 퀴즈 도중 뒤로가기 시 인트로로 빠지는 동선도 자연스럽다.

**공유·유입은 `/football/quiz` 로 직행**시킨다. `/football` 을 거치게 하면 클릭이 하나 늘어난다.

### 4.2 결과 화면 — Static Shell + Client Hydration

```
빌드/재검증  ──> 팀 데이터 조회 ──> 15장 미리 생성 ──┐
                                                    │
공유 링크 클릭 ──────────────────> 정적 HTML 즉시 ──┤ DB 왕복 0회
                                                    │
                          #a= 파싱 → 4축 다이아몬드 (CSR)
                          kit_post_url → 구단 공식 Instagram 게시물 (CSR · 뷰포트 진입 시)
```

```ts
export const revalidate = 86400; // 24시간

export function generateStaticParams() {
  return CLUBS.map((c) => ({ slug: c.slug })); // lib/clubs.ts — 백엔드 호출 없음
}
```

**`generateStaticParams` 에서 백엔드를 부르지 않는 이유**: 프론트 빌드가 백엔드 가용성에 묶이면 배포 순서 의존성이 생긴다. slug 15개는 이미 `lib/clubs.ts` 에 있다.

**답코드는 해시(`#a=`)라 서버에 도달하지 않는다** (§3.1). 팀 카드는 `slug` 만으로 서버에서, 그래프는 **클라이언트 컴포넌트**가 마운트 후 `window.location.hash` 를 읽어 그린다. `useSearchParams` 는 쓰지 않는다.

> 쿼리로 되돌리지 말 것 — Next 문서 원문: *"`searchParams` is a **Request-time API**... Using it will **opt the page into dynamic rendering** at request time."* (`page.md:119`). 서버 컴포넌트나 `generateMetadata` 에서 쿼리를 읽는 순간 ISR 이 사라지고 매 요청마다 서버가 돈다 — 바이럴 트래픽에서 정확히 피하고 싶은 상황이다.
>
> 🚨 **"답코드별 맞춤 OG" 는 만들지 않는다.** 해시는 서버에 오지 않아 읽을 수도 없다. **OG 는 팀 slug 단위로 만든다** (15장 정적 · 구성은 §8). 공유되는 가치는 *"어느 팀이냐"* 이지 축 점수가 아니다. 4축 다이아몬드는 클라이언트에서 그리면 충분하다.

#### 화면 구성

| 영역 | 내용 | 출처 |
|---|---|---|
| 정체성 선언 | **팀 컬러 배경** + "당신과 가장 닮은 팀은 ○○" + 캐치프레이즈 — 배지 없음 | 프론트(이름·컬러) + DB(카피) |
| 4축 다이아몬드 | 내 점수 vs 팀 좌표 | **프론트** (답코드 + `lib/clubs.ts`) |
| 팀 소개 | 정식명·연고지·창단·홈구장(이름만) | DB |
| 인물 | 감독 · 스타 · 레전드 + 기준일 | DB |
| **라이벌 팀** | 이름 + 한 줄 — **텍스트만** | `rivalSlug` + 라이벌 행의 DB 카피 |
| 행동 유도 | 공유 · **나도 해보기** · 다시하기 | — |
| **구단 공식 Instagram 게시물** | 당해 시즌 홈 유니폼 **사진** 게시물 1개를 통째로 임베드 + 대체 링크 + 독립 서비스 고지 1줄 — **맨 아래, 참고 자료** | DB `kit_post_url` + Instagram `embed.js` (**§4.7**) |

**엠블럼·배지 이미지는 어디에도 없다** — 유니폼 게시물 카드의 계정 사진과 셔츠에 보이는 것으로 충분하다. 왜 그런지는 §4.7 과 [LEGAL.md](LEGAL.md).

**"상극 팀"이 아니라 "라이벌 팀"이다.** `rivalSlug` 는 **좌표와 무관한 고정값**(전통 라이벌)이다. "상극"이라 부르면 사용자는 *내 성향과 정반대인 팀*을 기대하는데 실제로는 그게 아니라 **말과 내용이 어긋난다.**

🔑 **"나도 해보기"와 "다시하기"는 다른 버튼이다.** 대상이 다르다.

| 버튼 | 누구를 위한 것 | 어디로 |
|---|---|---|
| **나도 해보기** | **링크를 받고 온 사람** | 인트로 `/football/quiz` |
| 다시하기 | 방금 푼 사람 | 문항 처음부터 |

**바이럴 유입은 전부 전자**다. 링크를 받은 사람에게 "다시하기"는 말이 안 된다 — 한 적이 없으니까. 결과 화면이 **인트로로 돌아가는 순환 고리**를 만들어야 공유가 새 참여로 이어진다.

**2·3위 대안 팀은 보여주지 않는다.** `matchTeam` 은 우승 팀만 반환하며 그대로 둔다. MBTI식 단일 결과의 **확정감**이 공유 가치를 만들고, "2위와 0.02 차이"를 노출하면 신뢰가 흔들린다.

**참여 비율(%)은 넣지 않는다** — "23%가 같은 결과"는 최대 집단에게 *"너 흔해"* 로 읽힌다.

⚠️ **비율(%)과 팀 순위는 다르다.** 순위(`다른 사람들은 어떤 팀이 나왔을까?` Top N, **수치 없이 순서만**)는 **2차에 결과 화면에 넣기로 했다** — 공유로 들어온 사용자는 허브를 지나가지 않으므로 허브에만 두면 아무도 못 본다. MVP 범위는 아니지만 자리를 비워둘 것. 근거는 [FUTURE §2](FUTURE.md).

### 4.3 참여자 수 — 반드시 CSR

**서버에서 DB에 의존시키면 안 된다.** 결과 페이지를 ISR로 방어해놓고 입구를 열면 의미가 없다.

```
정적 셸    히어로 · 시작 버튼         ← 즉시 표시
CSR 영역   참여자 수                  ← 마운트 후 fetch
```

백엔드가 죽어도 퀴즈는 정상 동작해야 하며, 이 줄만 조용히 비면 된다.

**위치는 `/football/quiz` 인트로.** "이미 N명이 참여했어요"는 **시작 버튼 옆**에 있어야 전환에 기여한다.

`_components/ParticipantCount.tsx` 가 자리를 잡고 있으며 **지금은 `return null`** 이다. 구현 규칙은 그 파일 주석에 보존돼 있고 F6 에서 채운다.

**최소 표본 임계값이 필요하다.** 오픈 직후 "3명 참여"는 사회적 증거가 아니라 역효과다. 일정 수 이하면 숨긴다. (인물 데이터의 "오래되면 숨김"과 같은 원칙 — **없는 것보다 나쁜 게 초라한 것**)

### 4.4 참여 기록 — ISR 방어를 우회하지 않도록

읽기는 캐시로 막지만 **쓰기는 캐시가 못 막는다.** 결과 화면 진입마다 POST하면 트래픽이 그대로 DB에 도달하고, 새로고침·뒤로가기마다 중복 기록된다.

- **퀴즈 완료 시점에 1회만** 전송
- `sessionStorage` 로 중복 차단
- **fire-and-forget** — 응답을 기다리지 않는다. 실패해도 결과 화면에 영향 없음
- **답코드도 함께 보낸다** — 팀(`slug`)만이 아니라 9자리 답코드까지. 분석용이며 화면에는 쓰지 않는다(§5.2). 요청 본문 형태는 백엔드 F6-3 에서 확정

### 4.5 진행 화면 구현 (S5·S6에서 확정)

```
app/football/quiz/play/
├── page.tsx                    서버 — metadata · robots
├── _store.ts                   zustand — index · league · choices
├── QuizPlay.tsx                클라이언트 — 조립만
└── _components/
    ├── BipolarScale.tsx        Q2~Q9 척도 (§8.2)
    ├── CardChoices.tsx         Q1 카드    (S6-b)
    └── QuizProgress.tsx        진행바      (S6-b)
```

**라우트와 화면을 나눠야 한다** — `"use client"` 파일에서는 `metadata` 를 내보낼 수 없다. `page.tsx` 가 메타데이터를, 클라이언트 컴포넌트가 화면을 맡는다.

**한 라우트 + 상태 교체.** 문항마다 URL 을 두지 않는다 — 답이 URL 에 없으므로 `/play/5` 를 새로고침하면 *5번 문항인데 답 0개* 라는 모순 상태가 생긴다.

**`index`(현재 문항)를 스토어에 둔다.** 답과 위치는 항상 함께 움직인다. 컴포넌트 `useState` 로 쪼개면 자동 진행에서 두 갱신 시스템이 한 핸들러에 섞인다.

**자동 진행** — 선택 = 답 저장 + 다음 문항. "다음" 버튼 없음(탭 18회 → 9회).

**`← 이전`(한 칸)과 선택된 답 표시는 넣는다.** 자동 진행이라 오탭을 되돌릴 수단이 없으면 **잘못된 답으로 나온 결과가 공유**되고, 그건 이 서비스의 목표를 직접 해친다. 시각적 위계는 낮춘다(`text-gray-400`).

**완료 화면에는 `← 이전`을 두지 않는다** — 결과는 별도 라우트이고 `reset` 으로 답이 비워진다. "다시하기"로 처음부터가 맞다.

**`reset` 은 언마운트 정리로** (`useEffect(() => reset, [reset])`). 들어올 때 초기화하면 지난 완료 화면이 한 프레임 비친다.

⏸ **새로고침 시 답 유실은 "미룬 것"** — `persist` 미들웨어(sessionStorage)로 해결 가능하나 하이드레이션 깜빡임·낡은 답 복원 방어가 따라온다. 스토어 모양이 이미 저장하기 좋아 나중에 감싸기만 하면 되고 화면 코드는 안 바뀐다. 배포 후 완주율을 보고 결정.

### 4.6 컴포넌트를 어디에 둘까

**한 라우트만 쓰면 그 라우트의 `_components/`, 두 곳 이상이면 최상위 `components/`.**

- `BipolarScale` · `ParticipantCount` → 라우트 콜로케이션
- `ShareButtons` → 인트로 + 결과 두 곳에서 쓰므로 최상위

밑줄(`_`)은 Next 문법이다 — **private folder** 로 라우팅에서 제외된다. 안 붙이면 `app/` 안의 폴더 이름이 그대로 URL 이 된다. Next 문서는 컴포넌트 배치 자체에는 unopinionated 이므로 위 규칙은 이 프로젝트의 약속이다.

**파일 안에서만 쓰는 컴포넌트는 파일을 나누지 않는다** — `BipolarScale.tsx` 안의 `PoleText` · `ScaleDot` 은 `export` 없이 같은 파일에 둔다. 밖에서 쓰이면 그때 나눈다.

#### 구현 구조 (S8)

```
서버 컴포넌트(ISR)   kit_post_url ──> oEmbed 생존 확인(아래) ──> <KitEmbed permalink handle />
                                                          └ 영구 실패·NULL 이면 대체 링크만

KitEmbed (클라이언트)
  ① 대체 링크 <a href="https://www.instagram.com/{handle}/">Instagram에서 보기</a>
     — blockquote 밖 형제로 **항상** 렌더. 스크립트가 아예 안 돌아도 HTML 만으로 보인다
  ② <div dangerouslySetInnerHTML={{ __html }} />  — React 가 blockquote 를 다시 건드리지 않게
     __html 은 useMemo([permalink]) 로 고정 (렌더마다 새 객체면 innerHTML 이 재대입돼 iframe 이 사라진다)
  ③ IntersectionObserver(rootMargin 300px) 진입 시에만
     <Script src="https://www.instagram.com/embed.js" strategy="afterInteractive"
             onReady={() => window.instgrm?.Embeds?.process()} />
     — 진입 전엔 Meta 로 아무 요청도 가지 않는다 (§7.6 고지의 전제)
  ④ 성공 = iframe.instagram-media-rendered 등장(MutationObserver) → iframe.title = "○○ 공식 Instagram 게시물"
     실패 = Script onLoad 후 12초 내 rendered 없음 → ① 을 강조 (iframe 은 제거하지 않음)
```

- `embed.js` 는 blockquote **앞에** iframe 을 끼우고, 다 그려지면 blockquote 를 **지운다**. JSX 로 그린 blockquote 를 조건부로 빼거나 그 앞에 형제를 끼우면 React 가 깨진다 → ② 필수. StrictMode 이중 effect 로 `process()` 가 두 번 불려도 처리된 blockquote 는 클래스가 떼어져 no-op
- **폭**: 카드는 `calc(100% - 2px)`·최소 326px 유동(Preflight border-box 기준 실측 326px). 본문 327px 에선 넘치지 않지만 360px 폰(본문 312px)에서는 14px 넘친다 → 임베드 섹션만 거터를 조정해 326px 이 들어가게 하고, `overflow-hidden`·`min-width !important` 덮어쓰기는 금지. 공식 스니펫보다 좁은 폭은 Instagram 이 지원하지 않는다
- **높이**: blockquote(약 487px) → iframe(약 645px) 교체가 CLS 로 잡힌다 → 래퍼 `min-height` 예약. 게시물마다 다르므로 시즌 등록 때 실측(§7.1)
- **성능**: 카드 1장 전송량 약 1.8MB(iframe 문서 약 300KB + JS·CSS·이미지). 뷰포트 밖이라 LCP 영향은 없지만 ③ 지연 로드가 전제. Android WebView(카톡 인앱)는 iframe 이 같은 프로세스라 더 중요
- **CSP 를 켠다면** `script-src 'self' 'unsafe-inline' https://www.instagram.com; frame-src https://www.instagram.com; style-src 'self' 'unsafe-inline'; object-src 'none'` 이 최소(App Router 인라인 스크립트와 embed.js 인라인 스타일 때문). 논스 방식은 ISR 과 양립 불가 → `next.config.ts` `headers()` + `Report-Only` 로 먼저 관찰. 지금은 CSP 가 없다
- **oEmbed 생존 확인** (서버 · ISR 재생성 때 팀당 1회 = 하루 15회): `GET https://graph.facebook.com/v26.0/instagram_oembed?url={kit_post_url}&omitscript=true` — **2026-06-15 부터 토큰·앱 심사 없이** 호출 가능(시간당 1,000회). 응답은 저장하지 않는다. **영구 실패(HTTP 400 · `code 24` · `error_subcode 2207045` = 삭제·비공개·임베드 비활성)만** 대체 링크로 렌더하고, 네트워크·5xx·타임아웃·`is_transient: true` 는 임베드 유지 — Meta 장애가 폴백을 하루 동안 굳히지 않게. `fetch` 에 `cache: 'no-store'` 를 주면 페이지가 동적이 된다 → 기본 캐시(= 페이지 `revalidate`) 로. 토큰 없는 응답엔 계정명이 없어 **소유 계정 확인은 등록 때 수동**
- **실기기 매트릭스(출시 전 · §9)**: iOS Safari 일반/개인정보 보호 탭 · 카카오톡 인앱 iOS/Android · Instagram 인앱 · Firefox 엄격 모드 · Chrome Android. 2026-10-20 PC 크롬 390px 에서 1.5~2초 내 렌더 확인. 테스트 페이지 `C:\dev\embed-test\index.html`(`이현준` PC · git 밖)

## 5. 백엔드 설계

> **`category_slug` 선반영 원칙**: 카테고리 확장이 목표이므로 카테고리 종속 테이블에는 지금부터 이 컬럼을 넣는다. 비용은 컬럼 하나. MVP 값은 전부 `'football'`.
>
> 🚨 **"행 추가만으로 새 카테고리"가 성립하는 건 `participant_logs` 형태뿐이다.** `team_results` 는 `stadium`·`league_name`·`manager`·`legend` 처럼 **축구 전용 컬럼 덩어리**라 카메라·등산 행이 들어갈 수 없다 — `category_slug` 가 있어도 마찬가지다.
>
> | 테이블 | 다른 카테고리 행 |
> |---|---|
> | `participant_logs` (id·category_slug·result_slug·answer_code·created_at) | ✅ **완전 제네릭** |
> | `team_results` (축구 전용 컬럼 다수) | ❌ 불가 |
>
> 카테고리가 늘면 **`team_results` 를 늘리는 게 아니라 별도 구조로 간다.** [FUTURE §3](FUTURE.md) 의 제네릭 `items` + `extra JSON` 이 유력하지만 **⏸ 확정은 아니다** — `items` 는 원래 *UGC 입문템* 용이고, 퀴즈 결과 표시까지 겸할지는 정한 적이 없다. 4차에 결정한다.
>
> 지금 확실한 것 두 가지: `team_results` 의 `category_slug` 는 **확장용이 아니라 조회를 카테고리로 가르기 위한 것**이고, **`team_results` 에 범용 컬럼을 덧붙이는 방향으로 가면 안 된다.**

```sql
  -- ── 우리 카피 ───────────────────────────────────────
  catchphrase       VARCHAR(64)  NOT NULL,
  description       VARCHAR(500),              -- 광고 단계엔 자체 글이 임베드 카드보다 많아야 한다(FUTURE §6) → S8 에서 상한 재검토

  -- ── 인물 (docs/club-people-*.md 가 원천) ────────────
  manager           VARCHAR(32),
  manager_note      VARCHAR(48),
  star_player       VARCHAR(32),               -- 현 소속 필수 · 이적시장마다 점검
  star_player_note  VARCHAR(48),
  legend            VARCHAR(32),               -- 구단 역사 · 갱신 불필요
  legend_note       VARCHAR(64),               -- 검증 가능한 기록 근거 필수
  curated_at        DATE         NOT NULL,     -- 감독·스타 기준일 (§7.2)

  -- ── 구단 공식 Instagram (§4.7) ───────────────────────
  instagram_handle  VARCHAR(30)  NOT NULL,     -- 'mancity' → 대체 링크의 원천 · 항상 있다
  kit_post_url      VARCHAR(255) NULL UNIQUE,  -- 'https://www.instagram.com/p/DYjcda2jpzj/' · NULL = 표시할 게시물 없음 → 대체 링크만
  kit_season_start  SMALLINT     NULL,         -- 2026 → '2026/27' 라벨은 API/프론트에서 조립
  CHECK (kit_post_url IS NULL OR kit_post_url LIKE 'https://www.instagram.com/p/%/'),
  CHECK ((kit_post_url IS NULL) = (kit_season_start IS NULL))
);
```

**없앤 것** — `external_id`·`api_football_id`·`synced_at`·`badge_path`(TheSportsDB 동기화 영역 전체) · `color1~3`(→ 프론트 `lib/team-display.ts`, §7.4) · `short_code`·`stadium_capacity`·`location`·`country`·`instagram`(화면에 안 쓰거나 `instagram_handle` 로 대체). 배지가 사라지며 API 동기화의 효용이 없어졌고, 남는 사실 정보는 15행이라 손으로 넣는 게 싸다. 시즌마다 바뀌는 항목(감독·스타·유니폼 게시물)은 원래부터 수동이었다. TheSportsDB 를 쓰지 않으므로 출처 표기 의무도 없다.

**읽기 전용 테이블이다.** 런타임에 이 테이블을 쓰는 코드는 0개 — 엔티티는 setter 없이 `@org.hibernate.annotations.Immutable`(Hibernate ORM 애노테이션 · DB 벤더 기능이 아니라 규칙 위반 아님), Repository 는 조회 메서드만. 옛 설계의 "새 엔티티 `save()` 로 큐레이션을 날리는 사고"가 구조적으로 사라진다.

**데이터는 Flyway 시드 파일이 진실이다** (백엔드 `src/main/resources/db/migration/`).
- DDL 은 `V__`(`V1__participant_logs.sql` · `V2__team_results.sql`), **15행 데이터는 `R__team_results_seed.sql`**(`DELETE … WHERE category_slug = 'football'; INSERT … 15행` — 파일이 바뀔 때만 자동 재적용, InnoDB DML 이라 트랜잭션 하나로 전부-또는-전무). **DDL 과 DML 을 한 파일에 섞지 않는다** — MySQL 의 DDL 암묵적 커밋 때문에 실패 시 반쯤 적용된 채 남는다
- `INSERT … ON DUPLICATE KEY UPDATE` 같은 벤더 구문 ✗ (FUTURE §4 락인 방어)
- 운영 DB 를 직접 `UPDATE` 하면 다음 시드 변경 때 덮어써진다 → 반드시 파일에도 반영 (§7.1 런북 2단계)
- 시드 파일의 각 행에 **출처(공식 사이트 URL)·확인일** 을 주석으로 남긴다 — 시즌 갱신 때 재검증 근거

**`kit_post_url` 검증은 Java 에서.** 저장 전 쿼리스트링(`?igsh=`·`?utm_source=`)을 떼고 `https://www.instagram.com/p/{code}/` 로 정규화한 뒤 `^https://www\.instagram\.com/p/[A-Za-z0-9_-]+/$` 로 검사한다 — `/reel/`·`/tv/` 를 그대로 붙인 실수와 다른 호스트(CSP `frame-src` 가 막는다)를 잡는다. **사진 게시물인지는 정규식이 보장하지 못한다**(릴스 코드를 `/p/` 로 넣어도 영상이 렌더된다) → 등록 체크리스트 항목(§4.7 선정 기준). DB 의 `CHECK` 는 이식 가능한 `LIKE` 까지만 — 정규식 `CHECK` 는 DBMS 마다 문법이 달라 쓰지 않는다.

### 5.2 `participant_logs`

```sql
CREATE TABLE participant_logs (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  category_slug VARCHAR(32) NOT NULL,
  result_slug   VARCHAR(32) NOT NULL,
  answer_code   VARCHAR(32),             -- 답코드 원문(§3.1) · 분석용 · NULL 허용
  created_at    DATETIME    NOT NULL,    -- UTC
  INDEX idx_cat_slug (category_slug, result_slug),
  INDEX idx_created (created_at)
);
```

**⚠️ 참여자 수를 매 요청 `COUNT(*)` 하지 말 것.** 바이럴로 수십만 행이 쌓이면 체감된다. → **1분 TTL 캐시**(`@Cacheable`). 1분 늦게 갱신돼도 문제없다.

**`answer_code` — 분석을 위해 답까지 남긴다** (2026-10-06 추가)

팀만 기록하면 *"어느 팀이 나왔나"* 까지만 알 수 있다. 답코드가 있으면 **문항별 응답 분포**와, §8.1 감사가 가정한 응답 모델(균등·중앙편향·극단편향)이 **실제와 맞는지**를 볼 수 있다. **기록하지 않은 답은 나중에 되살릴 수 없으므로** 실제 참여를 받기 전에 넣는다.

- **백엔드는 해석하지 않는다.** 글자 그대로 보관할 뿐이다 — "채점·문항은 프론트"(§2) 원칙은 그대로다. 해석은 분석할 때 `lib/` 로 한다
- **`NULL` 허용** — 답코드가 없거나 형식이 틀려도 **참여 기록 자체는 남아야** 참여자 수가 틀리지 않는다. 프론트가 답코드를 보내기 전에 백엔드가 먼저 배포돼도 깨지지 않는다
- **길이 32** — 축구는 9자리지만 다른 카테고리의 퀴즈는 길이가 다를 수 있다. 이 테이블은 제네릭이어야 한다
- ⚠️ **문항을 바꾸면 옛 답코드의 뜻이 달라진다**(§3.3). 분석할 때는 `created_at` 으로 변경 전후를 나눠서 본다
- 개인정보가 아니다 — 누구의 답인지 알 수 없고, 답코드는 이미 공유 URL 에 노출되는 값이다

**`created_at` 은 UTC 로 저장한다** (2026-10-06). 로컬(KST)과 배포 서버의 시간대가 다르면 값이 섞이기 때문이다. DB 를 직접 보면 한국 시각보다 9시간 이르게 보인다.

이 테이블 하나가 나중에 허브의 팀 순위도 만든다 ([FUTURE §2](FUTURE.md)).

## 6. REST API 명세 (MVP)

베이스 `/api/v1`. 나머지 엔드포인트는 [FUTURE.md](FUTURE.md).

| 메서드 | 경로 | 용도 | 호출 주체 | CORS |
|---|---|---|---|---|
| GET | `/results` | **15팀 일괄** (빌드/ISR용) | Next 서버 | 불필요 |
| GET | `/results/{slug}` | 단건 (필요 시) | Next 서버 | 불필요 |
| GET | `/participants/count` | 참여자 수 (1분 캐시) | **브라우저** | 필요 |
| POST | `/participants` | 참여 기록 + 답코드 (완료 시 1회) | **브라우저** | 필요 |

**`GET /results/slugs` 는 만들지 않는다** — `generateStaticParams` 가 `lib/clubs.ts` 를 쓰므로 불필요하고, 빌드-백엔드 결합만 늘어난다.

**`/results` 를 일괄 조회로 둔 이유**: 빌드 시 15번 호출할 이유가 없다. 15행뿐.

**CORS**: 브라우저에서 직접 부르는 엔드포인트만 설정.

**`GET /results` 응답 형태** (F7 에서 확정 · 칸 이름은 §5.1 의 camelCase): `{ slug, nameEn, nicknameKo, locationKo, foundedYear, stadium, leagueName, catchphrase, description, manager, managerNote, starPlayer, starPlayerNote, legend, legendNote, curatedAt, instagramHandle, kit: { postUrl, seasonLabel: '2026/27' } | null }` — 이름·컬러·좌표는 넣지 않는다(프론트 원본).

**결과 페이지가 이 호출에 실패하면 삼키지 않고 던진다** (2026-10-20 · §9 #1 해소). 빌드는 실패하고(이전 배포 유지 — Vercel 은 성공한 배포만 승격) ISR 재생성은 마지막 성공본을 유지한다. `try/catch` 로 삼켜 폴백을 렌더하면 **열화된 페이지가 '성공'으로 24시간 캐시**된다. 따라서 **백엔드가 먼저 떠 있어야 S8 을 배포할 수 있다.** `AbortSignal.timeout()` 은 둔다. 백엔드 정지 위험은 [FUTURE §4](FUTURE.md) 유휴 회수 항목.

## 7. 운영

### 7.1 데이터 갱신 — 전부 수동 · 시드 파일이 진실 (§5.1)

| 대상 | 주기 | 방식 |
|---|---|---|
| **홈 유니폼 게시물** (`kit_post_url`·`kit_season_start`) | **연 1회 · 5~7월** (2026 년엔 5/4 바이에른 ~ 7/2 바르셀로나) | 아래 시즌 교체 절차 |
| **감독** | 경질 시 수시 | 시드 수정 |
| **스타 선수** | **이적시장 마감 후** (9월 초 · 2월 초) | 시드 수정 |
| 경기장명(스폰서)·리그명 | 바뀔 때 (몇 년에 한 번) | 시드 수정 |
| 레전드 · 창단 · 연고지 | 없음 | — |

**새 유니폼이 아직 안 나온 팀은 지난 시즌 게시물을 그대로 둔다.** 빈 카드보다 낡은 카드가 낫다(§4.3 과 같은 원칙).

#### 시즌 교체 절차 (팀당 5분)

1. Instagram 앱에서 구단 공식 계정(인증 배지 확인)의 새 홈 유니폼 게시물을 열고 **첫 장이 사진**인지 확인 → `…` → 링크 복사
2. `R__team_results_seed.sql` 의 `kit_post_url`·`kit_season_start` 수정 + 주석에 확인일 (쿼리스트링은 떼고 넣는다 — Java 가 정규화하지만 diff 가 지저분해진다)
3. 커밋 → 배포 (Flyway 가 PC 2대·운영 DB 를 같은 값으로 수렴)
4. `revalidatePath('/football/result/[slug]', 'page')` 를 부르는 비밀 토큰 Route Handler 호출(없으면 Vercel Redeploy) → 15개 결과 URL 을 한 번씩 방문해 즉시 재생성 — ISR 24h 는 "다음 방문자까지" 라 트래픽 적은 팀은 며칠 낡을 수 있다
5. 실기기에서 카드 높이 실측 → `min-height` 상수 갱신 (§4.7)
6. 같은 때 §7.6 의 제3자 수집도구 표가 현실과 맞는지 점검

#### 권리자 삭제 요청 런북 — 푸터 약속: **"요청 확인 후 24시간 이내"**

| 순서 | 행동 | 효과 |
|---|---|---|
| 1 | 운영 DB `UPDATE team_results SET kit_post_url = NULL, kit_season_start = NULL WHERE slug = '…'` | 다음 재생성부터 대체 링크만 |
| 2 | `R__team_results_seed.sql` 에 같은 변경 커밋·배포 | 파일이 진실 — 빠뜨리면 다음 시즌 교체 때 되살아난다 |
| 3 | `revalidatePath` 호출 또는 Vercel Redeploy | 15장 즉시 재생성 — "24시간 이내" 를 실제로 지키는 수단 |

DB 만 고치면 ISR 이 최대 하루 옛 카드를 내보낸다. 구단 쪽도 게시물 삭제·임베드 비활성으로 즉시 차단할 수 있고, oEmbed 생존 확인(§4.7)이 다음 재생성 때 이를 반영한다.

### 7.2 신선도 방어 (수동 데이터)

수동 데이터의 최대 위험은 **방치**. 팬 사용자는 틀린 정보를 즉시 알아채고, **사실 오류 하나가 채점 알고리즘 신뢰까지 무너뜨린다.**

1. **기준일 표기** — "감독·스타는 2026년 8월 기준". 낡아도 정직하면 신뢰가 유지된다
2. **오래되면 숨김** — `curated_at` 이 6개월 초과 시 감독·스타 섹션 미표시. **레전드는 항상 표시**하므로 인물 영역이 비지 않는다
3. **댓글이 제보 창구** — 팬이 "감독 바뀌었어요"를 알려준다

```
당신과 가장 닮은 팀은  ⟶  맨체스터 시티

감독     엔초 마레스카     펩의 제자, 점유율 축구 계승자
스타     엘링 홀란         한 시즌 36골 괴물 골잡이
레전드   세르히오 아구에로  구단 최다 득점 260골
                            감독·스타는 2026년 8월 기준
```

### 7.3 이미지 자산 — 두지 않는다 (2026-10-20)

- **이미지 파일을 레포·DB·CDN 어디에도 두지 않는다** — 배지·엠블럼·유니폼·경기장·선수 전부. `public/badges/` 는 만들지 않는다. 팀 이미지는 §4.7 임베드가 유일하고, 임베드도 저장·캡처·썸네일 금지. 경기장은 이름만(사진 ✗ — Commons CC BY-SA 도 파일별 표기 관리 비용 때문에 기각)
- **선수 사진은 넣지 않는다** (초상권·퍼블리시티)
- `next.config` `images.remotePatterns` 에 `instagram.com`·`cdninstagram.com` 계열 ✗ — `next/image` 는 원격 이미지를 서버가 받아 캐시하므로 그 순간 우리가 복제·전송한 것이 된다
- OG 이미지(15장 정적)의 입력은 팀 이름 + 팀 컬러 + `newbeez.kr` 뿐 (§8)
- 외부 데이터 출처 표기 푸터는 **필요 없어졌다** — TheSportsDB 를 쓰지 않는다. 대신 §7.6 의 독립 서비스 고지를 둔다

### 7.4 색상 사용 주의

`color2` 가 `#FFFFFF` 인 팀이 다수(첼시·레알·토트넘 등). 흰 배경에 그대로 쓰면 보이지 않는다. → **대비 검사 후 테두리 추가 또는 배경 반전.**

팀 색은 **표시 전용**이며 매칭에는 쓰지 않는다. `lib/clubs.ts`(매칭 모듈)가 아니라 **`lib/team-display.ts`** 에 둔다 — 2026-10-20 에 DB 에서 프론트로 옮겼다: 백엔드 없이 히어로·OG 15장을 만들 수 있어야 하고, 15개 색상값은 거의 바뀌지 않는다. 원천은 구단 공식 사이트·유니폼의 대표색이며 색상값 자체는 권리 대상이 아니다. **색만 쓴다** — 엠블럼 형태·유니폼 스트라이프 패턴 재현 ✗ (§4.7).

### 7.5 한국어 표기 규칙

**원칙: 한국 축구 매체가 정식 기사에서 쓰는 이름.** 국립국어원 표기법(아궤로·판데이크)이나 원어 발음 근접보다 우선한다 — 사용자가 **검색해본 적 있는 이름**이어야 알아보기 때문. 개별 정확성보다 **15장 카드 전체의 일관성**이 중요하다.

#### 팀명 — 이름은 한 곳에만

**`lib/clubs.ts` 의 `name` 이 표시명의 유일한 원본.** 화면은 항상 여기서 가져온다.

- 백엔드가 죽어도 "당신과 가장 닮은 팀은 ○○" 까지는 나와야 하므로 프론트에 있어야 한다
- `team_results.name_ko` 는 **운영 참조용 사본** — DB를 볼 때 slug만 보이면 불편해서 두는 것이고 **화면에 쓰지 않는다**
- **약칭 필드는 만들지 않는다.** 필요해지면 그때 추가한다. 미리 만들면 "같은 것에 이름 둘" 문제가 다시 생긴다 (실제로 `아스날`/`아스널` 어긋남이 그렇게 발생했다)

| slug | name | slug | name |
|---|---|---|---|
| man-city | 맨체스터 시티 | real-madrid | 레알 마드리드 |

### 8.1 척도 UI — 세로축 4점

**Q2~Q9 양극 척도는 세로로 배치한다.**

```
      걸어 잠근다!                         ← 위쪽 극 (headline + detail)
      실리적으로 역습을 노리며 승리를 굳힌다

              ⬤   완전히 위쪽    (큰 원)
              ●   약간 위쪽      (작은 원)
              ●   약간 아래쪽    (작은 원)
              ⬤   완전히 아래쪽  (큰 원)

      몰아친다!                            ← 아래쪽 극
      추가골을 노려 경기를 끝내버린다
```

**근거**

1. **세로가 극단 응답을 늘린다** — 양 끝 사이의 **시각적 거리가 가로에서 더 멀기** 때문. 확정 설계의 "점들을 가운데로 압축(끝이 멀면 극단적으로 느껴져 회피)" 규칙과 **같은 원리**이고, 중립을 없앤 짝수 척도의 취지와 같은 방향
2. **응답 부담이 낮다** — 응답 시간·신뢰도 기준으로 가로가 더 부담스럽다. 완주율이 생명인 서비스에서 유의미
3. **327px 폭에서 `detail` 텍스트가 산다** — 가로였다면 극당 약 120px에 4줄로 쪼개진다
4. **Q1(3지선다)과 일관된다** — Q1은 선택지가 긴 문장이라 세로 외 답이 없으므로, 9문항 내내 조작법이 같아진다

> 출처: [Extremity in horizontal and vertical Likert scale format responses](https://www.sciencedirect.com/science/article/abs/pii/S0167811620300367) · [Hu 2020](https://journals.sagepub.com/doi/abs/10.1177/0894439319834296) · [MeasuringU](https://measuringu.com/horizontal-vs-vertical-rating-scales/)

**방향 규칙**: `왼쪽=음수 / 오른쪽=양수` → **`위=음수 / 아래=양수`**. 90도 돌릴 뿐 의도(방향 고정·역채점 금지)는 그대로이며 **데이터는 안 바뀐다** (`ChoiceIndex` 0이 맨 위, 3이 맨 아래).

**안쪽 2점 라벨 — 화면에는 노출하지 않는다.** 극단 2개의 라벨은 위/아래 극 문구(`headline` + `detail`)가 맡고, 안쪽 2개는 **원 크기와 축 위 위치**로 읽힌다.

> **2026-08-26 결정.** 한때 "전점 라벨 상시 노출"로 뒤집었다가(안쪽이 무엇인지 알 수 없다는 우려) **원래 설계로 되돌렸다.** 시안을 실제로 그려 보니 *극 문구 + 원 크기 + 축 위 위치*만으로 의미가 전달되고, 텍스트 4줄이 화면을 시끄럽게 만들었다. 근거는 원래대로 *전점 라벨이 가운데를 매력적으로 만들어 극단 선택을 끌어내린다(Weijters 2010)*.
>
> **2026-08-30 후속 결정 — `Pole.word` 는 삭제됐다.** 한때 "화면에는 없지만 `aria-label`에 쓴다"고 남겨뒀으나, MVP에서 **접근성 라벨을 넣지 않기로** 정하면서(§8.4) 읽는 코드가 0곳이 됐다. 안 쓰는 데이터를 남기면 `colorCode` 때와 같은 일이 반복되므로 17줄을 지웠다. 되살리려면 `Pole` 인터페이스와 8문항 × 2극을 함께 복원해야 한다.

- **점 크기(큰-작은-작은-큰)와 가운데 압축**은 유지해 극단 쪽 유인을 남긴다
- 🚨 **일반 설문과 반대다.** 보통 설문은 극단 응답을 *줄이려* 하는데 이 척도는 *늘리려* 한다. **원이 큰 쪽이 극단**이다 — 헷갈려서 "극단을 막으려 안쪽을 키운 것"으로 오독한 적이 있다

#### ⚠️ 극단 유도의 근거 정정 (2026-09-10 실측)

한때 *"극단 응답이 팀 분포를 고르게 한다"* 는 취지로 읽혔으나 **전수 감사로 확인해보니 사실이 아니다.**

| 응답 모델 | EPL | ETC | **ALL** | 굶는 팀 |
|---|---|---|---|---|
| 균등 (기준선) | 2.38 | 2.69 | **4.39** | 0 |
| 중앙편향 ×4 | 2.44 | 2.72 | 4.43 | 0 |

- **중앙만 가도 나빠진다**(4.71배). 즉 **한쪽 쏠림이 문제지 극단 여부가 아니다** — 분포를 살리는 건 *응답의 다양성*이다

🔑 **그럼 극단 유도는 무엇을 지키나 — 4축 다이아몬드 그래프다.** 팀 매칭은 안 바뀌지만 그래프는 크기를 그대로 보여준다. 가운데만 고르면 마름모가 쪼그라들어 *"이게 나다"* 하는 **확정감이 사라진다**(§4.2가 2·3위를 숨기는 것과 같은 논리). 분포가 아니라 **결과의 선명함**이 목적이다.

> **원 크기는 실기기 피드백으로 두 번 키웠다** (48/32 → 56/36 → **80/48**, 2026-08-31·09-01). 데스크톱에서 적당해 보이던 크기가 실기기에서는 계속 작았다. **시안 실측값(58/36)보다도 크다** — 시안은 참고이지 정답이 아니다.
>
> 안쪽 원 **48px** 은 터치 권장 최소치(44px)를 넘는다. **오탭 위험이 설계상 사라졌다** — 자동 진행이라 오탭이 즉시 확정되는 구조에서 이게 중요하다.
>
> **짧은 화면 자동 축소** — `[@media(max-height:600px)]:size-12` 처럼 **높이** 미디어쿼리로 원을 한 단계 줄인다. Tailwind 기본 반응형(`sm:` `md:`)은 전부 **폭** 기준이라 이 경우엔 못 쓴다. (v4 임의 변형, at-rule 에는 `&` 불필요)
>
> 🔑 **이 분리 덕에 일반 화면의 원을 키워도 iPhone SE 세로 예산에 영향이 없다.** 짧은 화면은 48/32 로 고정되므로 두 값을 독립적으로 정할 수 있다.
>
> 🚨 **`justify-center` 를 바깥 컨테이너에 쓰지 말 것.** 남는 세로 공간이 덩어리 *바깥*(질문 아래 + `← 이전` 위)으로 갈라져 들어가, 390×844 실기기에서 **질문과 극 문구 사이가 166px** 벌어졌다. 대신 **축 영역이 `flex-1` 로 흡수**하고 `max-h` 로 상한을 둔다.
>
> **상한은 "축의 최대 길이"(400px · `max-h-100`)로 건다** — 화면 높이에서 헤더를 뺀 값으로 역산하면 진행바·질문 배치가 바뀔 때마다 틀어진다.
>
> **축선을 축 영역 끝까지(`inset-y-0`) 늘리는 게 핵심.** 여백을 선이 채우면 "빈 곳"이 아니라 **"긴 축"** 으로 읽힌다. 시안이 원 뭉치보다 훨씬 긴 선을 그린 이유가 이것이다.

**축선이 원 안에서 끊겨 보이게 하는 네 가지** — 하나만 빠져도 선이 원을 관통한다.

| | 역할 |
|---|---|
| 선 `absolute` | 배치 흐름에서 빠져 자리를 차지하지 않음 |
| 컨테이너 `relative` | 그 선의 **좌표 기준점** |
| 원 `relative` | 선과 **같은 층**으로 올려 "나중에 그려진 쪽이 위" 규칙을 적용 |
| 원 `bg-white` | 실제로 선을 **가리는** 것 |

`z-index` 는 쓰지 않는다 — DOM 순서(선이 먼저, 원이 나중)만으로 해결되고, `z-index` 는 값이 흩어지면 추적이 어려워진다.

> 🚨 **"극단↔안쪽 24px / 안쪽↔안쪽 8px"은 시안 오독이었다 (폐기).** 실제로 8px로 그리면 안쪽 두 원이 붙어 보인다. 시안 PDF를 픽셀 단위로 다시 재보니 **간격은 균일**했다.
>
> **"가운데 압축"은 간격이 아니라 원 크기가 만든다.** 간격이 전부 24px이어도 안쪽 원이 작아서 **중심 간 거리가 64 / 56 / 64** 로 저절로 좁아진다. §8.1이 요구한 "점 크기(큰-작은-작은-큰)"와 "가운데 압축"은 **서로 다른 두 장치가 아니라 같은 하나**였다. 간격까지 좁히면 압축이 두 번 걸린다.

> **클릭 영역은 원 자체로 간다 (2026-08-30).** "행 전체 + 44px 터치 영역" 안은 채택하지 않았다. 안쪽 원의 터치 영역이 32px로 권장치(44px) 미달인 것은 **인지된 위험**이며, 실기기에서 오탭이 잦으면 `p-1.5` 같은 투명 여백으로 44px을 확보한다(원 크기·간격은 그대로 유지 가능).

> **`short:` 접두사** — `app/globals.css` 의 `@custom-variant short (@media (max-height: 600px));` 로 등록했다. 기준값 600 은 **이 한 곳에만** 있다. 대괄호 `[@media(max-height:600px)]:` 와 컴파일 결과가 같다(Tailwind 4.3.0 확인). Tailwind 기본 반응형(`sm:` `md:`)은 전부 **폭** 기준이라 높이 조건은 직접 등록해야 한다.

### 8.3 배경 이미지 — 진행 화면에는 쓰지 않는다 (2026-08-26 검토)

일러스트 4종(경기장·훈련장·감독실·라커룸)을 진행 화면 배경으로 실험했고 **S6에서 다시 판단하기로 보류**했다. 임시 화면 위에서 본 판단은 신뢰할 수 없기 때문(아래 참고).

> 파일은 `바탕화면/레퍼런스/배경후보/` 에 있다. `public/` 에서 옮긴 이유는 **쓰지도 않는 6.6MB가 배포에 딸려 나가기** 때문(`public/` 은 통째로 빌드 산출물에 복사됨). **S6에서 채택하면 WebP로 변환해 다시 `public/` 으로.**

- **적합도**: 경기장 > 훈련장 ≫ 감독실 > 라커룸. 실내 이미지는 디테일이 촘촘하고 **강한 원근 사선이 척도의 수직 축선과 충돌**하며 밝기가 불균일하다
- 🚨 **1a와 궁합이 나쁘다** — 1a는 카드가 없어 **극 문구·`← 이전`이 배경 위에 맨몸으로** 놓인다. 하필 그 자리가 배경의 명도가 갈리는 곳(위=하늘·아래=잔디)이고, `detail`은 `text-xs` 회색이라 가장 먼저 깨진다. 흰 원도 밝은 하늘 위에서 존재감을 잃어 **네 점이 대등해 보여야 한다는 요건**이 무너진다
- **검토가 왜 왜곡됐었나**: 임시 카드 화면 위에서 보면 선택지가 흰 카드로 보호돼 **실제보다 안전해 보인다**. 배경을 다시 검토할 일이 생기면 반드시 **1a를 구현한 뒤 그 위에서** 볼 것
- 쓸 자리는 여전히 열려 있다 — **인트로→퀴즈 전환 화면**(감독실) · 결과 페이지 상단 · (여유되면) 문항별 배경. **진행 화면만 제외**
- ⚠️ **용량**: 4장 모두 PNG 1.4~1.8MB. 어디에 쓰든 **WebP 변환 필수**(약 90% 감소) + `next/image` 경유(CSS `background-image`는 최적화 대상이 아님)
