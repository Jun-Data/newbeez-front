## 0. 서비스 컨셉 (오해 주의)

**재는 것은 사용자 본인의 성향, 내주는 것은 닮은 팀.**

사용자가 *감독으로 팀에 입단해* 문항에 답하는 연출을 쓰지만, **감독은 가벼운 스킨일 뿐 측정 대상이 아님**. "당신은 이런 감독입니다"가 아니라 **"당신과 가장 닮은 팀은 ○○입니다"**가 결과다. MBTI식 단일 정체성 카드.

따라서 4축(전술·자원·조직·목표)도 "감독으로서의 전술 성향"이 아니라 **사용자 성향을 축구 언어로 옮긴 좌표**로 읽어야 한다.

### '감독님' 호칭은 퀴즈 화면 전용

| 화면 | '감독'이 가리키는 것 | 표기 |
|---|---|---|
| **퀴즈 진행 (Q1~Q9)** | 사용자 본인 | "감독님" 호칭 사용 |
| **랜딩 · 결과** | 구단 감독 (`manager` 컬럼) | "감독" 그대로 |

결과 화면에서는 사용자를 "감독님"이라 부르지 않으므로 "감독 펩 과르디올라"는 자연스럽게 구단 감독으로 읽힌다. **용어를 따로 분리할 필요 없음.**

> 결과 화면에서 사용자를 무엇으로 부를지(예: "당신")는 카피 작업(S7)에서 확정.

## 2. 역할 분담 — 무엇이 어디에 있고 왜

| 데이터 | 소유 | 이유 |
|---|---|---|
| **문항·선택지·배점** | 프론트 (`lib/`) | 답코드 URL 계약과 결박됨. 문항 수가 바뀌면 기존 공유 링크가 깨짐 → 앱과 함께 배포되어야 함 |
| **팀 좌표·리그·라이벌** | 프론트 (`lib/clubs.ts`) | 채점 입력. 네트워크 없이 즉시 계산해야 함 |
| **채점 로직** | 프론트 (순수함수) | 마지막 클릭 → 결과까지 왕복 0회. 전수 감사(65,536건) 가능 |
| **팀 표시 정보** | 백엔드 DB | 외부 API 출처 + 이미지 자산 + 갱신 필요 |
| **참여자 수·댓글** | 백엔드 DB | 실시간 집계·쓰기 |

### 핵심 원칙

**계산은 프론트, 표시 데이터는 백엔드.** 사용자 답을 백엔드로 보내 추천 결과를 받아오는 구조가 **아님**.

두 층을 잇는 계약은 **`slug`** (`man-city`, `chelsea` …). `lib/clubs.ts`와 `team_results`가 서로를 몰라도 slug 하나로 연결됨. 팀을 추가할 때만 양쪽을 함께 수정.

## 3. 퀴즈 코어 (이미 완성 — 재작성 금지)

`quiz-data.ts` 같은 새 파일을 만들지 말 것. **이미 5개 파일로 구현·검증 완료됨.**

| 파일 | 내용 |
|---|---|
| `lib/types.ts` | 공용 타입. **`AXES` = 4축** (tactics, resource, organization, goal) |
| `lib/clubs.ts` | 15팀 좌표·리그·라이벌 |
| `lib/scoring-config.ts` | 배점표 · `AXIS_SCALE` · `COS_BAND` |
| `lib/questions.ts` | 9문항 판별 유니온 (Q1 리그 + Q2~Q9 성향) |
| `lib/scoring.ts` | `matchTeam` — 코사인 방향 + 밴드 내 유클리드 타이브레이크 |
| `scripts/audit.ts` | 65,536 전수 감사 → `pnpm quiz:audit` |

**DoD 통과 상태**: 굶는 팀 0 · EPL 2.4배 · ETC 2.7배 · ALL 4.4배 · 균등/중앙편향 둘 다 통과.

### 답안 코드 규격

```
/football/result/man-city?a=032104213
                            │└──────┘
                            │   └──── Q2~Q9 성향 8자리 (각 0~3)
                            └──────── Q1 리그 필터 1자리 (0=EPL · 1=ETC · 2=ALL)
```

- **9자리** = 리그 1 + 성향 8 (2026-08-11 결정)
- **Q1을 포함하는 이유 — 이게 없으면 재현·검증이 불가능하다.** Q1은 후보 팀 풀을 정하므로 **같은 성향 점수라도 리그가 다르면 다른 팀이 나온다.** 리그가 빠지면 `matchTeam` 을 다시 돌릴 수 없고, 아래 같은 조작 링크를 막을 방법이 없다:

```
/football/result/man-city?a=000000000
                  ↑ 맨시티 카드      ↑ 실제로는 다른 팀이 나올 답
```

- **검증**: 클라이언트에서 답코드로 `matchTeam` 을 재실행해 경로의 `slug` 와 대조한다. 채점 함수가 프론트에 있으므로 **추가 비용 0**. 불일치·파싱 실패 시 **그래프 영역만 생략**하고 팀 카드는 정상 렌더 (페이지가 깨지면 안 됨)
- ⚠️ **URL은 한번 공유되면 못 바꾸는 계약.** 자릿수·인코딩은 첫 배포 전에 확정할 것

#### ⚠️ 구현 시 반드시 처리할 것 (2026-08-11 코드 검토에서 발견)

현재 `lib/` 코드는 **유효한 입력만 들어온다고 가정**한다. 답코드 파싱을 붙이는 순간 조작된 URL이 그 가정을 깨뜨린다.

| # | 위치 | 무슨 일이 나나 |
|---|---|---|
| 1 | `lib/scoring.ts` `matchTeam` — `ranked[0].cos` | 리그 자리가 잘못되면 `pool` 이 **빈 배열** → `undefined` 접근 → **페이지 전체가 죽는다** |
| 2 | `lib/scoring.ts` `scoreAxes` — `ITEM_VALUES[q.slot][choices[q.id]]` | 답이 4 이상이면 `undefined` → **NaN 이 4축 전체로 전파** → 그래프가 깨진다 |

**→ 검증은 `matchTeam` 을 호출하기 *전에* 파싱 단계에서 해야 한다.** 자릿수·문자 범위(리그 0~2, 성향 0~3)를 먼저 확인하고, 실패하면 `matchTeam` 을 아예 부르지 않는다.

| # | 사항 | |
|---|---|---|
| 3 | **문항 순서는 배포 후 고정** | 답코드 자릿수가 `QUESTIONS` 배열 순서에 대응한다. 순서를 바꾸면 **이미 공유된 링크가 전부 다른 결과를 가리킨다.** 전수 감사는 모든 조합을 돌아 순서에 무관하므로 **감사로는 이 사고를 잡을 수 없다** |
- 각 자리는 `ChoiceIndex = 0 | 1 | 2 | 3` — **4 이상은 무효**
- 파싱 실패 시 그래프 영역만 생략하고 나머지는 정상 렌더 (페이지가 깨지면 안 됨)

### 그래프는 4축 다이아몬드

축이 4개이므로 **사각형(다이아몬드)**. 오각형이 아님. 5번째 축 추가는 설계상 기각됨(채점 엔진·감사 전면 재작업 발생).

## 4. 프론트엔드 설계

### 4.1 라우팅

**3단 계층**: 카테고리 홈 → 카테고리 → 테스트. 러닝화·키보드 확장 시 같은 모양으로 늘어난다.

| 경로 | 파일 | 역할 | 렌더링 |
|---|---|---|---|
| `/` | `app/page.tsx` | **카테고리 홈** — 해외축구·러닝화·키보드… | 정적 |
| `/football` | `app/football/page.tsx` | **해외축구 입문 허브** — §4.5 참고 | 정적 셸 + CSR |
| `/football/quiz` | `app/football/quiz/page.tsx` | **테스트 인트로** — 히어로·시작 버튼. **공유·유입의 착지점** | 정적 셸 + CSR |
| `/football/quiz/play` | `app/football/quiz/play/page.tsx` | 퀴즈 진행 (Q1~Q9) | 클라이언트 단독 |
| `/football/result/[slug]` | `app/football/result/[slug]/page.tsx` | 결과 | ISR + CSR 오버레이 |

**인트로(`/quiz`)와 진행(`/quiz/play`)을 나누는 이유**: 인트로는 **공유되고 색인되는 페이지**라 OG 메타데이터·정적 생성 대상이고, 진행 화면은 클라이언트 상태 덩어리라 성격이 정반대다. 나눠두면 퀴즈 도중 뒤로가기 시 인트로로 빠지는 동선도 자연스럽다.

**공유·유입은 `/football/quiz`로 직행**시킨다 (결과 화면의 "나도 해보기" 등). `/football`을 거치게 하면 클릭이 하나 늘어난다. `/football`은 탐색·SEO용 경로다.

### 4.2 결과 화면 — Static Shell + Client Hydration

```
빌드/재검증  ──> GET /api/v1/results ──> 15장 미리 생성 ──┐
                                                          │
공유 링크 클릭 ────────────────────────> 정적 HTML 즉시 ──┤ DB 왕복 0회
                                                          │
                            ?a= 파싱 → 4축 다이아몬드 오버레이 (CSR)
```

```ts
// app/football/result/[slug]/page.tsx
export const revalidate = 86400; // 24시간

export function generateStaticParams() {
  return CLUBS.map((c) => ({ slug: c.slug })); // lib/clubs.ts — 백엔드 호출 없음
}
```

**`generateStaticParams`에서 백엔드를 부르지 않는 이유**: 프론트 빌드가 백엔드 가용성에 묶이면 배포 순서 의존성이 생김. slug 15개는 이미 `lib/clubs.ts`에 있음.

**쿼리스트링 주의**: 서버 컴포넌트에서 `?a=`를 읽으면 정적 생성이 깨짐.
→ 팀 카드는 `slug`만으로 서버에서, 그래프는 **클라이언트 컴포넌트**에서 `useSearchParams`로 읽어 렌더.

#### 결과 화면 구성

| 영역 | 내용 | 출처 |
|---|---|---|
| 정체성 선언 | 배지 + "당신과 가장 닮은 팀은 ○○" + 캐치프레이즈 | DB + 우리 카피 |
| 4축 다이아몬드 | 내 점수 vs 팀 좌표 | **프론트** (답코드 + `lib/clubs.ts`) |
| 팀 소개 | 정식명·연고지·창단·홈구장 | DB |
| 인물 | 감독 · 스타 · 레전드 | DB |
| **라이벌 팀** | 배지 + 한 줄 | `rivalSlug` + DB |
| 행동 유도 | 공유 · 다시하기 · 허브로 | — |
| 댓글 | 결과별 스레드 (§4.3) | DB · CSR |

**"상극 팀"이 아니라 "라이벌 팀"이다** (2026-08-11 결정). `lib/clubs.ts` 의 `rivalSlug` 는 **좌표와 무관한 고정값**(전통 라이벌)이다. "상극"이라 부르면 사용자는 *내 성향과 정반대인 팀*을 기대하는데 실제로는 그게 아니므로 **말과 내용이 어긋난다.**

**2·3위 대안 팀은 보여주지 않는다** (2026-08-11 결정). `matchTeam` 은 우승 팀만 반환하며 그대로 둔다. MBTI식 단일 결과의 **확정감**이 공유 가치를 만들고, "2위와 0.02 차이"를 노출하면 신뢰가 흔들린다.

**결과 화면에는 참여 비율(%)을 넣지 않는다** — 근거는 §4.5.

### 4.3 소셜 영역(참여자 수·댓글) — 반드시 CSR

**어느 페이지든 서버에서 DB에 의존시키면 안 됨.** 결과 페이지를 ISR로 방어해놓고 입구를 열면 의미가 없다. 백엔드가 죽어도 퀴즈는 정상 동작해야 하며, 소셜 영역만 조용히 비거나 스켈레톤을 유지한다.

**배치 확정 (2026-08-11)**

| 요소 | 위치 | 이유 |
|---|---|---|
| **참여자 수** | `/football/quiz` 인트로 | "이미 N명이 참여했어요"는 **시작 버튼 옆**에 있어야 전환에 기여 |
| **댓글** | `/football/result/[slug]` 결과 | 이상형 월드컵 방식 — **같은 팀이 나온 사람들끼리 모임** |

**댓글은 결과별 스레드다.** `comments.result_slug` 로 15개 스레드가 생기며, 답코드가 달라도 팀이 같으면 한 방에 모인다.

> 15개로 쪼개지므로 사용자가 적을 때 열면 전부 빈 방이 된다. **댓글을 MVP 맨 마지막에 두는 이유**가 여기 있다.

**참여자 수도 최소 표본 임계값이 필요하다.** 오픈 직후 "3명 참여"는 사회적 증거가 아니라 역효과다. 일정 수 이하면 이 줄을 숨긴다. (인물 데이터의 "오래되면 숨김"과 같은 원칙 — **없는 것보다 나쁜 게 초라한 것**)

**카톡 공유에는 댓글이 실리지 않는다.** 공유되는 건 OG 태그로 만든 **미리보기 카드(이미지+제목+설명)** 뿐이며, 링크를 눌러 들어와야 댓글이 보인다.

### 4.4 참여 기록 — ISR 방어를 우회하지 않도록

읽기는 캐시로 막지만 **쓰기는 캐시가 못 막음.** 결과 화면 진입마다 POST하면 트래픽이 그대로 DB에 도달하고, 새로고침·뒤로가기마다 중복 기록됨.

- **퀴즈 완료 시점에 1회만** 전송 (결과 화면 진입마다 ❌)
- `sessionStorage`로 중복 차단
- **fire-and-forget** — 응답을 기다리지 않음. 실패해도 결과 화면에 영향 없음

### 4.5 `/football` — 입문 허브 (제품의 본체)

> **퀴즈는 입구고 카테고리 허브가 본체다.** 서비스 정체성은 "입문의 정석" — 뭘 골라야 할지 막막한 뉴비를 위한 가이드이며, 퀴즈는 그 안의 도구 하나다. `app/layout.tsx` 의 설명문이 이 정체성을 이미 담고 있다.

**허브 전체가 MVP 이후다.** 핵심 동선(인트로 → 퀴즈 → 결과 → 공유)에 허브가 없기 때문. 공유 링크를 타고 온 사용자는 허브를 지나가지 않는다. MVP 동안 `/football` 은 **히어로 + 퀴즈로 가는 버튼**만 있는 얇은 안내 페이지로 둔다.

| 섹션 | 내용 | 데이터 | 렌더링 |
|---|---|---|---|
| 히어로 + 퀴즈 시작 버튼 | | 없음 | 정적 |
| **입문 꿀팁** | 뉴비가 카테고리를 이해하는 정보 — 축구 규칙, 리그별 설명, 용어 등 | 우리가 쓴 글 | 정적 |
| **퀴즈 결과 팀 순위** | 퀴즈로 많이 나온 팀 | `participant_logs` 집계 | CSR + 캐시 |
| **입문팀 추천 순위** | 사람들이 뉴비에게 권하는 팀 (§4.6) | UGC | CSR |
| 커뮤니티 게시판 | | UGC | CSR |

**팀 순위가 둘이라는 점에 주의.** 하나는 *알고리즘이 준 답*, 하나는 *사람들의 추천*이라 성격이 다르다. 라벨을 확실히 구분해야 하며, 둘이 어긋나는 것 자체가 콘텐츠가 된다.

**팀 순위는 추가 스키마가 필요 없다** — `participant_logs` 에서 `GROUP BY result_slug` 한 번이면 나온다. 허브를 열 때 바로 붙일 수 있다.

**미루는 이유 — 닭과 달걀**: 순위·추천·게시판 모두 사용자가 있어야 의미가 있다. 오픈 첫날 "참여자 3명 · 게시글 0개"는 사회적 증거가 아니라 **버려진 서비스**로 읽힌다. 퀴즈로 트래픽을 만들고 → 데이터가 쌓이면 순위를 열고 → 사람이 모이면 커뮤니티를 여는 순서.

> **15팀 그리드는 넣지 않는다** (2026-08-11 결정). 옛 HANDOFF S3 계획에 있던 항목. 결과를 미리 보여주면 기대감이 깎이고, 배지 15장 확보(S2)에 묶인다.

**결과 화면에는 비율(%)을 넣지 않는다** (2026-08-11 결정). 1위 팀은 참여자의 20% 이상이라 "23%가 같은 결과"는 **최대 집단에게 "너 흔해"로 읽힌다.** 결과 화면은 "너는 이 팀이야"라는 **선언**에 집중하고, 순위는 허브에서만 보여준다. 대신 결과 → 허브 링크(`다른 사람들은 어떤 팀이 나왔을까?`)로 동선을 잇는다.

### 4.6 입문템 추천 순위 + 인증 — 설계 방향 (MVP 제외)

**나무위키형 UGC.** 운영자가 후보를 띄우고 투표받는 방식이 **아니라**, 사용자가 직접 등록하고 다른 사용자가 인정(추천)해 순위가 만들어진다. 우리가 큐레이션하면 블로그지만 사용자가 만들면 커뮤니티 자산이 되고, 이게 복제하기 어려운 해자가 된다.

**"입문템" 정의**: 그 취미를 시작할 때 **처음 고르는 것**. 물건에 한정되지 않는다 — 러닝=러닝화(제품) · 애니=입문작(콘텐츠) · 등산=초보 코스(장소) · **축구=입문팀**.

**축구의 입문템은 팀이며, 추천 대상은 우리 15팀으로 한정한다** (2026-08-11 결정). 나폴리·아약스 등 외부 팀은 받지 않는다. 그러면 `items` 대신 `team_results` 를 그대로 재사용할 수 있어 중복 등록(위험 #1)도 원천 차단된다 — 등록 행위가 "새 항목 생성"이 아니라 "15개 중 고르기 + 추천 이유 쓰기"가 되기 때문이다.

> 다른 카테고리(러닝화·카메라)는 자유 등록이므로 아래 `items` 스키마가 필요하다. **축구만 특수 케이스**로, 15팀 한정이 주는 안전함을 취한다.

#### 열기 전에 반드시 해결할 것

| # | 위험 | 대응 |
|---|---|---|
| 1 | **중복 등록** — "나이키 페가수스"/"페가수스 41"/"나이키 페가수스 41"이 셋으로 쪼개져 순위가 무의미해짐. UGC 랭킹의 1번 실패 모드 | 등록 시 유사 항목 제안 + `merged_into` 로 병합·추천수 합산 |
| 2 | **스팸·광고** — 익명 등록은 자기 상품 홍보로 이어짐. 커머스 성격 카테고리(러닝화·카메라)가 특히 위험 | 로그인 필수 + 등록 문턱(최소 설명 길이) + 신고 |
| 3 | **어뷰징** — 자기 등록물 자추 | 로그인 + `UNIQUE(item_id, user_id)` |
| 4 | **콜드 스타트 역설** — "사용자가 만든다"와 "처음부터 비어 있다"는 다르다. **빈 화면에는 아무도 첫 번째로 쓰지 않는다** | 우리가 5~10개 **마중물**을 등록하되 등록 창구는 열어둠. 목록 통제가 아니라 본보기 제공 |

#### 인증 — 카카오 소셜 로그인

**자체 회원가입을 하지 않는다.** 이메일을 받아서 우리가 할 일이 없는데(메일 발송·마케팅 안 함) 비밀번호 보관 책임·재설정 흐름·이메일 인증만 떠안게 된다.

| | 자체 회원가입 | **소셜 로그인** |
|---|---|---|
| 비밀번호 저장 | 우리 책임 | **없음** |
| 이메일 인증 / 재설정 | 필요 | 불필요 |
| 가입 문턱 | 폼 + 인증 메일 | **카카오 3초** |

**문턱은 필요한 곳에만 건다.** 로그인을 전부에 걸면 서비스가 죽는다.

| 행동 | 로그인 |
|---|---|
| 퀴즈 풀기 · 결과 보기 · 공유 | **절대 요구 안 함** |
| 댓글 쓰기 | 익명 + 비밀번호 (그대로 유지) |
| **입문템 등록** | **필수** — 익명 등록은 광고판이 됨 |
| **입문템 추천** | **필수** — 순위의 신뢰가 이 기능의 존재 이유. 숫자만 크고 못 믿을 순위는 없느니만 못함 |

**도입 시점 = 입문템을 열 때.** 인증이 필요한 유일한 기능이 입문템이고 그건 어차피 나중이므로, 지금 넣으면 MVP만 몇 주 밀린다.

> ⚠️ CLAUDE.md 의 "무거운 인프라(인증)는 명시적 요청 전엔 도입하지 않음" 조항 — 2026-08-11 사용자가 **명시적으로 요청**하여 이 단계에 한해 해제.

#### 스키마 방향 (확정 아님)

```sql
items (
  id, category_slug, name, summary, recommend_reason,
  image_path, external_url, extra JSON,   -- 카테고리별 고유 속성
  status,          -- ACTIVE | MERGED | HIDDEN
  merged_into,     -- 중복 병합 대상
  endorse_count,   -- 비정규화 캐시
  created_by,      -- users.id
  created_at
)
item_endorsements (item_id, user_id, created_at, UNIQUE(item_id, user_id))
users (id, provider, provider_uid, nickname, created_at)
```

**카테고리별 테이블(`running_shoes`, `cameras`…)로 나누지 않는다.** 카테고리를 늘리는 게 서비스의 목표인데, 그 방식은 카테고리마다 테이블·엔티티·API를 새로 만들어야 해 **확장 비용이 가장 비싸다.** 공통 컬럼 + `extra JSON` 으로 흡수하고, 순위·추천은 공통 컬럼만 쓰므로 JSON 내부를 쿼리할 일이 거의 없다.

## 5. 백엔드 설계

> **`category_slug` 선반영 원칙**: 카테고리 확장이 서비스의 목표이므로, 카테고리에 종속되는 테이블에는 지금부터 `category_slug` 컬럼을 넣어둔다. 비용은 컬럼 하나, 이득은 나중에 러닝·카메라를 **마이그레이션 없이 행 추가만으로** 여는 것. MVP 값은 전부 `'football'`.

### 5.1 `team_results` — 하이브리드 한 테이블

```sql
CREATE TABLE team_results (
  -- ── API 동기화 영역 (배치가 건드림) ─────────────────
  slug             VARCHAR(32) PRIMARY KEY,   -- 'man-city' (프론트와의 계약 키)
  category_slug    VARCHAR(32) NOT NULL,      -- 'football' (선반영)
  external_id      VARCHAR(16) NOT NULL,      -- TheSportsDB idTeam
  api_football_id  VARCHAR(16),               -- 다른 API로 가는 다리
  name_en          VARCHAR(64),
  short_code       CHAR(3),                   -- 'MCI'
  founded_year     SMALLINT,
  stadium          VARCHAR(64),
  stadium_capacity INT,
  location         VARCHAR(64),
  country          VARCHAR(32),
  league_name      VARCHAR(64),
  color1           CHAR(7),
  color2           CHAR(7),
  color3           CHAR(7),
  badge_path       VARCHAR(128),              -- '/badges/man-city.png' (우리 자산)
  instagram        VARCHAR(128),
  synced_at        DATETIME,

  -- ── 수동 큐레이션 영역 (배치가 절대 안 건드림) ───────
  name_ko          VARCHAR(32) NOT NULL,      -- '맨시티'
  nickname_ko      VARCHAR(32),
  location_ko      VARCHAR(32),
  catchphrase      VARCHAR(64),
  description      VARCHAR(500),
  manager          VARCHAR(32),
  manager_note     VARCHAR(48),
  star_player      VARCHAR(32),               -- 현 소속 필수 · 이적시장마다 점검
  star_player_note VARCHAR(48),
  legend           VARCHAR(32),               -- 구단 역사 · 갱신 불필요
  legend_note      VARCHAR(64),               -- 검증 가능한 기록 근거 필수 (최장 41자, 여유 확보)
  curated_at       DATETIME                   -- manager·star_player 기준일
);
```

**⚠️ 한 테이블로 합친 대가 — 배치에 규율이 필요합니다.**

동기화 Service는 **메서드 하나로 좁히고, 기존 엔티티를 로드해 API 영역 setter만 호출**할 것.
새 엔티티를 만들어 `save()` 하면 **수동 큐레이션 컬럼이 전부 날아감.** 이게 미러링 패턴의 1번 사고.

**`synced_at` / `curated_at` 분리 이유**: 자동/수동 데이터의 신선도를 따로 판단해야 화면에 정확한 기준일을 표기하고 오래된 섹션만 숨길 수 있음.

### 5.2 `participant_logs`

```sql
CREATE TABLE participant_logs (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  category_slug VARCHAR(32) NOT NULL,   -- 'football' (선반영)
  result_slug   VARCHAR(32) NOT NULL,
  created_at    DATETIME    NOT NULL,
  INDEX idx_cat_slug (category_slug, result_slug),
  INDEX idx_created (created_at)
);
```

**⚠️ 참여자 수를 매 요청 `COUNT(*)` 하지 말 것.** 바이럴로 수십만 행이 쌓이면 체감됨.
→ **1분 TTL 캐시** (`@Cacheable`). 참여자 수가 1분 늦게 갱신돼도 아무 문제 없음.

**이 테이블 하나가 허브의 팀 순위(§4.5)도 만든다** — 추가 스키마 없음:

```sql
SELECT result_slug, COUNT(*) AS cnt
FROM participant_logs WHERE category_slug = 'football'
GROUP BY result_slug ORDER BY cnt DESC;
```

결과는 **사용자별로 다르지 않은 15행**이라 캐시가 완벽히 먹는다. 참여자가 백만이어도 DB는 1분에 한 번만 읽는다.

### 5.3 `comments`

```sql
CREATE TABLE comments (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  category_slug VARCHAR(32)  NOT NULL,   -- 'football' (선반영)
  result_slug   VARCHAR(32)  NOT NULL,   -- 결과별 스레드 (§4.3)
  nickname      VARCHAR(20)  NOT NULL,
  password      VARCHAR(60)  NOT NULL,   -- BCrypt 해시
  content       VARCHAR(300) NOT NULL,
  created_at    DATETIME     NOT NULL,
  deleted       BOOLEAN      DEFAULT FALSE,
  INDEX idx_thread (result_slug, created_at DESC)
);
```

**`result_slug` 로 스레드가 갈린다** — 맨시티가 나온 사람들은 맨시티 결과 페이지에서만 서로의 댓글을 본다. 답코드가 달라도 팀이 같으면 한 방이다.

- **비밀번호는 BCrypt.** 평문 저장 금지.
- **삭제는 `POST /comments/{id}/delete`** — `DELETE ...?password=xxx`는 비밀번호가 **서버 접근 로그에 남음**.
- **익명 + 공개 = 스팸·욕설 무방비.** 최소한 IP 기준 rate limit(예: 분당 3건) + 길이 제한은 필요.
- 물리 삭제 대신 `deleted` 플래그 → 사고 시 복구 가능.

## 6. REST API 명세

베이스: `/api/v1`

| 메서드 | 경로 | 용도 | 호출 주체 | CORS |
|---|---|---|---|---|
| GET | `/results` | **15팀 일괄** (빌드/ISR용) | Next 서버 | 불필요 |
| GET | `/results/{slug}` | 단건 (필요 시) | Next 서버 | 불필요 |
| GET | `/participants/count` | 참여자 수 (1분 캐시) | **브라우저** | 필요 |
| GET | `/participants/ranking` | **팀 순위 15행** (1분 캐시) — 허브 §4.5 | **브라우저** | 필요 |
| POST | `/participants` | 참여 기록 (완료 시 1회) | **브라우저** | 필요 |
| GET | `/comments?resultSlug=` | **결과별** 댓글 목록 (페이지네이션) | **브라우저** | 필요 |
| POST | `/comments` | 댓글 작성 (`resultSlug` 포함) | **브라우저** | 필요 |

**제거됨**: `GET /results/slugs` — `generateStaticParams`가 `lib/clubs.ts`를 쓰므로 불필요. 빌드-백엔드 결합만 늘어남.

**`/results`를 일괄 조회로 둔 이유**: 빌드 시 15번 호출할 이유가 없음. 15행뿐.

**CORS**: 브라우저에서 직접 부르는 엔드포인트만 설정. `/results`는 Next 서버에서만 부르므로 대상 아님.

## 7. 운영

### 7.1 데이터 갱신 주기

| 대상 | 주기 | 방식 |
|---|---|---|
| 팀 기본 정보 (배지·경기장·색) | 시즌 단위 (연 2회) | 배치 / 수동 트리거 |
| **감독** | 경질 시 수시 | 수동 |
| **스타 선수** | **이적시장 마감 후 연 2회** (9월 초 · 2월 초) | 수동 |
| 레전드 | 없음 | — |

**갱신 실패 시 기존 값을 덮어쓰지 말 것.** 팀 단위 부분 성공 허용.

### 7.2 신선도 방어 (수동 데이터)

수동 데이터의 최대 위험은 **방치**. 팬 사용자는 틀린 정보를 즉시 알아채고, 사실 오류 하나가 채점 알고리즘 신뢰까지 무너뜨림.

1. **기준일 표기** — "감독·스타는 2026년 8월 기준". 낡아도 정직하면 신뢰 유지
2. **오래되면 숨김** — `curated_at`이 6개월 초과 시 감독·스타 섹션 미표시. **레전드는 항상 표시**하므로 인물 영역이 비지 않음
3. **댓글이 제보 창구** — 팬이 "감독 바뀌었어요"를 알려줌

화면 예시:

```
당신과 가장 닮은 팀은  ⟶  맨체스터 시티

감독     펩 과르디올라     점유율 축구의 창시자
스타     엘링 홀란드       한 시즌 36골 괴물
```

### 7.4 한국어 표기 규칙

## 8. UI 방침

**모바일 우선.** 바이럴 트래픽은 거의 전부 모바일이고 공유도 카톡에서 일어난다. 데스크톱은 중앙 정렬된 모바일 폭(`max-w-md` 수준)으로 대응하면 충분하다. 참고 서비스: **푸망 · 방구석연구소** — 세로 스크롤, 큰 터치 타깃, 카톡 공유 중심, 결과 카드 이미지.

**다크모드는 지원하지 않는다** (MVP 한정, 추후 재검토).
⚠️ **"안 만들면 되는" 게 아니다.** Tailwind v4 는 OS 설정(`prefers-color-scheme`)을 따라가므로, 다크모드를 켠 사용자에게 **색이 반쯤 뒤집힌 화면**이 나올 수 있다. **라이트 고정을 명시**해야 의도대로 보인다.

**공유**

| | 하는 일 | 시점 |
|---|---|---|
| **OG 태그** | 링크를 붙여넣으면 미리보기 카드가 뜸 | **MVP 필수** |
| **카카오 SDK** | "카카오톡으로 공유하기" **버튼** | 배포 도메인 확정 직후 |

한국 바이럴은 카톡이 거의 전부이며 **버튼 유무가 공유율을 크게 가른다** — 링크를 복사해 붙여넣는 사용자는 드물다. 카카오 개발자 콘솔에 **배포 도메인 등록**이 선행되어야 하므로 도메인이 정해진 뒤 붙인다.

푸망·방구석연구소의 **결과 이미지 저장** 기능은 **동적 OG 이미지**(로드맵 S10)로 상당 부분 대체된다 — 공유 카드 자체가 내 결과를 담으면 별도 저장 기능이 덜 필요하다.

### 8.1 척도 UI — 세로축 4점 (2026-08-11 확정)

**Q2~Q9 양극 척도는 세로로 배치한다.** 위 극 ↔ 아래 극 사이에 선택지 4개.

```
      걸어 잠근다!                         ← 위쪽 극 (headline + detail)
      실리적으로 역습을 노리며 승리를 굳힌다

              ⬤   완전히 위쪽    (큰 원)
              ●   약간 위쪽      (작은 원)
              ●   약간 아래쪽    (작은 원)
              ⬤   완전히 아래쪽  (큰 원)

      몰아친다!                            ← 아래쪽 극
      추가골을 노려 경기를 끝내버린다
```

**근거**

1. **세로가 극단 응답을 늘린다.** 양 끝 선택지 사이의 **시각적 거리가 가로에서 더 멀기** 때문. 이는 확정 설계의 "점들을 가운데로 압축(끝이 멀면 극단적으로 느껴져 회피)" 규칙과 **같은 원리**이며, 중립을 없앤 짝수 척도의 취지와 같은 방향이다.
2. **응답 부담이 낮다.** 응답 시간·신뢰도·초두 효과 기준으로 가로가 더 부담스럽다. 완주율이 생명인 바이럴 테스트에서 유의미하다.
3. **327px 폭에서 `detail` 텍스트가 산다.** 가로였다면 극당 약 120px에 4줄로 쪼개진다.
4. **Q1(3지선다)과 레이아웃이 일관된다.** Q1은 선택지가 긴 문장이라 세로 외 선택지가 없으므로, 9문항 내내 조작법이 같아진다.

> 출처: [Extremity in horizontal and vertical Likert scale format responses](https://www.sciencedirect.com/science/article/abs/pii/S0167811620300367) · [Hu 2020, Horizontal or Vertical?](https://journals.sagepub.com/doi/abs/10.1177/0894439319834296) · [MeasuringU](https://measuringu.com/horizontal-vs-vertical-rating-scales/)

**방향 규칙 변경**: `왼쪽=음수 / 오른쪽=양수` → **`위=음수 / 아래=양수`**.
방향을 90도 돌릴 뿐 의도(방향 고정·역채점 금지)는 그대로다. **데이터는 안 바뀐다** — `ChoiceIndex` 0이 맨 위, 3이 맨 아래.

#### 안쪽 2점 라벨 — 상시 노출 (2026-08-11 사용자 결정)

네 선택지 **모두에 라벨을 상시 표시**한다. 안쪽 2개는 `questions.ts` 의 `Pole.word` 를 써서 `약간 실리적` / `약간 공세적` 형태로 적는다.

> ⚠️ **이는 기존 확정 설계를 덮는 결정이다.** 원래는 "양 끝만 라벨, 안쪽은 점만"이었고 근거는 *전점 라벨이 가운데를 매력적으로 만들어 극단 선택을 끌어내린다(Weijters 2010)* 였다. **사용자가 이해도를 우선해 상시 라벨을 선택했다** — 라벨이 없으면 안쪽 2개가 무엇인지 알 수 없다는 판단.

**대가와 완화**

- 대가: 중앙 쏠림이 늘 수 있다. 아시아 응답자 특성상 특히.
- 완화 ①: 안쪽 라벨의 **시각적 위계를 낮춘다** — 작은 글씨·낮은 대비. 읽을 수는 있되 눈에 먼저 들어오지 않게.
- 완화 ②: 확정된 **점 크기(큰-작은-작은-큰)와 가운데 압축**은 그대로 유지하여 극단 쪽 유인을 남긴다.
- 안전망: `pnpm quiz:audit` 이 **중앙편향 모델**(안쪽 답에 2배 가중)에서도 통과한 상태다. 중앙 쏠림이 실제로 늘어도 **팀 분포가 무너지지 않음이 이미 검증**되어 있다.

## 9. MVP 경계

```
MVP 포함   퀴즈 인트로(+참여자 수) · 퀴즈 진행 · 결과 화면 · 공유(OG)
MVP 마지막  익명 댓글 (결과별 스레드)
MVP 제외   /football 허브 전체 — 꿀팁 · 팀 순위 · 입문팀 UGC · 게시판
           인증(카카오) · 다른 카테고리 · 15팀 그리드 · 다크모드
지금 잡아둠 URL 계층 /<category>/... · DB category_slug 컬럼 · 답코드 9자리
```

**핵심 동선(인트로 → 퀴즈 → 결과 → 공유)만 MVP다.** 허브는 그 동선에 없으므로 이후로 미룬다. MVP 동안 `/football` 은 히어로 + 퀴즈 버튼만 있는 얇은 안내 페이지.

**축구 하나만 만들되 구조는 미리 잡는다.** `category_slug` 컬럼 하나면 나중에 러닝·카메라를 마이그레이션 없이 열 수 있다.

### 단계별

```
1차   프론트 + 최소 백엔드(참여 로그·팀 데이터)     퀴즈 동선 완결·공유 가능
2차   익명 댓글 → 허브 오픈(꿀팁·팀 순위)
3차   카카오 인증 + 입문팀 UGC → 커뮤니티 게시판
4차   다른 카테고리 (러닝·카메라…)
```

> 1차부터 참여 로그를 쌓아야 2차에서 팀 순위가 **0이 아닌 숫자로** 시작한다. 이것이 최소 백엔드를 1차에 함께 띄우는 이유.

### 백엔드 호스팅 조사 결과 (2026-08-11 · 결정 보류)

MVP는 백엔드 없이 완결되므로 지금 확정할 필요가 없다. 다만 **A1 인스턴스 확보가 복불복**(수시간~수일 실패)이라 필요해진 뒤 시작하면 그때 막힌다 → **미리 시도해둘 것.**

**1순위: Oracle Cloud Always Free (서울)** — A1 2 OCPU/12GB + MySQL HeatWave Always Free 50GB
「무료 + 서울 리전 + 진짜 MySQL + 콜드스타트 0 + **자동 과금 없음** + 기한 없음」 6가지를 동시에 만족하는 유일한 후보. 한도 초과 시 과금이 아니라 **생성 차단·정지**로 동작한다. 상용화 전환도 콘솔에서 PAYG 버튼 하나 — 인스턴스·DB·IP 그대로라 **마이그레이션 0**.

- 대가: 배포 난이도 HARD(SSH·systemd·nginx 직접 운영) · A1 확보 복불복 · **홈 리전은 가입 시 1회 확정이라 반드시 서울 선택**
- ⚠️ 2026-06-15에 4 OCPU/24GB → **2 OCPU/12GB로 축소**됨. 온라인 가이드 대부분이 옛 수치 기준이니 그대로 따라 하지 말 것

**2순위: Cloud Run(서울) + TiDB Cloud Starter(도쿄)** — A1을 못 잡거나 "git push 배포"가 더 중요할 때. 단 콜드스타트 5~15초, 지출 하드 상한 없음(`--max-instances` 필수), TiDB는 MySQL **호환**이라 트리거·프로시저 금지.

**피할 것**: Render(**MySQL 없음**·무료 DB 30일 만료) · AWS Free plan(**6개월 뒤 계정 폐쇄**) · Railway(무료 월 $1 = 4~6일치) · Fly.io·PlanetScale·Koyeb(무료 폐지/차단) · Gabia·Cafe24(**JDK 21 미지원** / JVM 256MB)

**락인 방어 — 어디를 고르든 지금부터 적용**: Dockerfile 컨테이너화 · DB 접속은 환경변수로만 · Flyway로 스키마 코드화 · **트리거·프로시저·벤더 함수 금지**. 가장 아픈 락인은 Postgres로 넘어가는 것(DDL·SQL·JPA 방언 전면 재작업).
