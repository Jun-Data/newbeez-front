## 0. 서비스 컨셉 (오해 주의)

**재는 것은 사용자 본인의 성향, 내주는 것은 닮은 팀.**

사용자가 *감독으로 팀에 입단해* 문항에 답하는 연출을 쓰지만 **감독은 가벼운 스킨일 뿐 측정 대상이 아니다.** "당신은 이런 감독입니다"가 아니라 **"당신과 가장 닮은 팀은 ○○입니다"**가 결과다. MBTI식 단일 정체성 카드.

따라서 4축(전술·자원·조직·목표)도 "감독으로서의 전술 성향"이 아니라 **사용자 성향을 축구 언어로 옮긴 좌표**로 읽는다.

**'감독님' 호칭은 퀴즈 진행 화면 전용.** 랜딩·결과에서는 사용자를 그렇게 부르지 않으므로, 결과의 "감독 엔초 마레스카"는 자연스럽게 구단 감독으로 읽힌다 — 용어를 따로 분리할 필요 없음.

## 2. 역할 분담

**계산은 프론트, 표시 데이터는 백엔드.** 사용자 답을 백엔드로 보내 결과를 받아오는 구조가 **아니다.**

| 데이터 | 소유 | 이유 |
|---|---|---|
| 문항·선택지·배점 | 프론트 `lib/` | 답코드 URL 계약과 결박됨 → 앱과 함께 배포되어야 함 |
| 팀 좌표·리그·라이벌 | 프론트 `lib/clubs.ts` | 채점 입력. 네트워크 없이 즉시 계산 |
| 채점 로직 | 프론트 (순수함수) | 마지막 클릭 → 결과까지 왕복 0회. 전수 감사 가능 |
| 팀 표시 정보 | 백엔드 DB | 외부 API 출처 + 이미지 자산 + 갱신 필요 |
| 참여자 수 | 백엔드 DB | 실시간 집계 |

두 층을 잇는 계약은 **`slug`** (`man-city`, `chelsea` …). `lib/clubs.ts` 와 `team_results` 가 서로를 몰라도 slug 하나로 연결된다.

## 3. 퀴즈 코어 (완성됨)

| 파일 | 내용 |
|---|---|
| `lib/types.ts` | 공용 타입. **`AXES` = 4축** (tactics, resource, organization, goal) |
| `lib/clubs.ts` | 15팀 좌표·리그·라이벌 + **표시명 원본** |
| `lib/scoring-config.ts` | 배점표 · `AXIS_SCALE` · `COS_BAND` |
| `lib/questions.ts` | 9문항 판별 유니온 (Q1 리그 + Q2~Q9 성향) |
| `lib/scoring.ts` | `matchTeam` — 코사인 방향 + 밴드 내 유클리드 타이브레이크 |
| `lib/answer-code.ts` | 답 ⇄ 9자리 문자열 변환·검증 |
| `scripts/audit.ts` · `audit-answer-code.ts` | 전수 감사 → `pnpm quiz:audit` |

**감사 통과 상태**: 굶는 팀 0 · EPL 2.38배 · ETC 2.69배 · ALL 4.39배 · 균등/중앙편향 둘 다 · 답코드 왕복 196,608건.

### 3.1 답코드 규격

```
/football/result/man-city?a=032104213
                            │└──────┘
                            │   └──── Q2~Q9 성향 8자리 (각 0~3)
                            └──────── Q1 리그 1자리 (0=EPL · 1=ETC · 2=ALL)
```

- **9자리** = 리그 1 + 성향 8
- **Q1을 포함하는 이유** — Q1이 후보 팀 풀을 정하므로 **같은 성향 점수라도 리그가 다르면 다른 팀이 나온다.** 리그가 빠지면 `matchTeam` 을 재현할 수 없어 `slug` 대조 검증이 불가능하다
- **검증**: 클라이언트에서 답코드로 `matchTeam` 을 재실행해 경로의 `slug` 와 대조. 채점 함수가 프론트에 있으므로 **추가 비용 0**
- 파싱 실패·불일치 시 **그래프 영역만 생략**하고 팀 카드는 정상 렌더 (페이지가 깨지면 안 됨)
- ⚠️ **URL은 한번 공유되면 못 바꾸는 계약**

### 3.2 ⚠️ 결과 화면 구현 시 반드시 처리할 것

`lib/scoring.ts` 는 **유효한 입력만 들어온다고 가정**한다. 조작된 URL이 그 가정을 깨뜨린다.

| 위치 | 무슨 일이 나나 |
|---|---|
| `matchTeam` — `ranked[0].cos` | 리그 자리가 잘못되면 `pool` 이 **빈 배열** → `undefined` 접근 → **페이지 전체가 죽는다** |
| `scoreAxes` — `ITEM_VALUES[q.slot][choices[q.id]]` | 답이 4 이상이면 `undefined` → **NaN 이 4축 전체로 전파** |

**→ `decodeAnswerCode` 가 `null` 을 뱉으면 `matchTeam` 을 아예 부르지 않는다.** 검증은 이미 `lib/answer-code.ts` 안에 있으므로, 화면은 `null` 여부만 확인하면 된다.

### 3.3 문항을 손댈 때의 규칙

| 변경 | 답코드 영향 | 대응 |
|---|---|---|
| 문항 **텍스트** 수정 | 없음 | 자유롭게 |
| 문항 **추가·삭제** | 자릿수가 바뀜 | 옛 링크는 `decode` 가 `null` → 그래프만 생략 |
| 문항 **순서** 변경 | 자리의 의미가 뒤바뀜 | 🚨 옛 링크가 다른 그래프를 그림 |
| 문항 **축·배점** 변경 | **자릿수는 그대로인데 의미만 달라짐** | 🚨 가장 위험 — 길이로도 못 걸러내고 에러도 안 남 |

**`scripts/audit-answer-code.ts` 가 이 사고를 막는다.** 계약(`EXPECTED_LEAGUES` · `EXPECTED_SCALE_IDS` · `EXPECTED_AXIS_SLOT`)을 하드코딩해 두고 `questions.ts` 와 대조하므로, 위 3·4번을 저지르면 `pnpm quiz:audit` 이 즉시 실패한다. **조용히 깨지는 것을 시끄럽게 깨지도록** 바꾸는 장치다.

> ⚠️ **왕복 전수 감사만으로는 못 잡는다.** 모든 조합을 도는 검사라 순서가 바뀌어도 왕복은 여전히 성공한다. 그래서 계약 대조가 따로 필요하다.

### 3.4 그래프는 4축 다이아몬드

축이 4개이므로 **사각형**. 오각형이 아니다. 5번째 축 추가는 기각됨(채점 엔진·감사 전면 재작업).

## 4. 프론트엔드 설계

### 4.1 라우팅

**3단 계층**: 카테고리 홈 → 카테고리 → 테스트. 다른 카테고리도 같은 모양으로 늘어난다.

| 경로 | 역할 | 렌더링 |
|---|---|---|
| `/` | 카테고리 홈 | 정적 |
| `/football` | 해외축구 — **MVP에선 히어로 + 퀴즈 버튼만** ([FUTURE §2](FUTURE.md)) | 정적 |
| `/football/quiz` | **테스트 인트로** — 히어로·시작 버튼·참여자 수. **공유·유입의 착지점** | 정적 셸 + CSR |
| `/football/quiz/play` | 퀴즈 진행 (Q1~Q9) | 클라이언트 단독 |
| `/football/result/[slug]` | 결과 | ISR + CSR 오버레이 |

**인트로와 진행을 나누는 이유**: 인트로는 **공유되고 색인되는 페이지**라 OG 메타데이터·정적 생성 대상이고, 진행 화면은 클라이언트 상태 덩어리라 성격이 정반대다. 퀴즈 도중 뒤로가기 시 인트로로 빠지는 동선도 자연스럽다.

**공유·유입은 `/football/quiz` 로 직행**시킨다. `/football` 을 거치게 하면 클릭이 하나 늘어난다.

### 4.2 결과 화면 — Static Shell + Client Hydration

```
빌드/재검증  ──> 팀 데이터 조회 ──> 15장 미리 생성 ──┐
                                                    │
공유 링크 클릭 ──────────────────> 정적 HTML 즉시 ──┤ DB 왕복 0회
                                                    │
                          ?a= 파싱 → 4축 다이아몬드 (CSR)
```

```ts
export const revalidate = 86400; // 24시간

export function generateStaticParams() {
  return CLUBS.map((c) => ({ slug: c.slug })); // lib/clubs.ts — 백엔드 호출 없음
}
```

**`generateStaticParams` 에서 백엔드를 부르지 않는 이유**: 프론트 빌드가 백엔드 가용성에 묶이면 배포 순서 의존성이 생긴다. slug 15개는 이미 `lib/clubs.ts` 에 있다.

**쿼리스트링 주의**: 서버 컴포넌트에서 `?a=` 를 읽으면 정적 생성이 깨진다. → 팀 카드는 `slug` 만으로 서버에서, 그래프는 **클라이언트 컴포넌트**에서 `useSearchParams` 로.

#### 화면 구성

| 영역 | 내용 | 출처 |
|---|---|---|
| 정체성 선언 | 배지 + "당신과 가장 닮은 팀은 ○○" + 캐치프레이즈 | DB + 우리 카피 |
| 4축 다이아몬드 | 내 점수 vs 팀 좌표 | **프론트** (답코드 + `lib/clubs.ts`) |
| 팀 소개 | 정식명·연고지·창단·홈구장 | DB |
| 인물 | 감독 · 스타 · 레전드 | DB |
| **라이벌 팀** | 배지 + 한 줄 | `rivalSlug` + DB |
| 행동 유도 | 공유 · 다시하기 | — |

**"상극 팀"이 아니라 "라이벌 팀"이다.** `rivalSlug` 는 **좌표와 무관한 고정값**(전통 라이벌)이다. "상극"이라 부르면 사용자는 *내 성향과 정반대인 팀*을 기대하는데 실제로는 그게 아니라 **말과 내용이 어긋난다.**

**2·3위 대안 팀은 보여주지 않는다.** `matchTeam` 은 우승 팀만 반환하며 그대로 둔다. MBTI식 단일 결과의 **확정감**이 공유 가치를 만들고, "2위와 0.02 차이"를 노출하면 신뢰가 흔들린다.

**참여 비율(%)도 넣지 않는다** — 근거는 [FUTURE §2](FUTURE.md).

### 4.3 참여자 수 — 반드시 CSR

**서버에서 DB에 의존시키면 안 된다.** 결과 페이지를 ISR로 방어해놓고 입구를 열면 의미가 없다.

```
정적 셸    히어로 · 시작 버튼         ← 즉시 표시
CSR 영역   참여자 수                  ← 마운트 후 fetch
```

백엔드가 죽어도 퀴즈는 정상 동작해야 하며, 이 줄만 조용히 비면 된다.

**위치는 `/football/quiz` 인트로.** "이미 N명이 참여했어요"는 **시작 버튼 옆**에 있어야 전환에 기여한다.

**최소 표본 임계값이 필요하다.** 오픈 직후 "3명 참여"는 사회적 증거가 아니라 역효과다. 일정 수 이하면 숨긴다. (인물 데이터의 "오래되면 숨김"과 같은 원칙 — **없는 것보다 나쁜 게 초라한 것**)

### 4.4 참여 기록 — ISR 방어를 우회하지 않도록

읽기는 캐시로 막지만 **쓰기는 캐시가 못 막는다.** 결과 화면 진입마다 POST하면 트래픽이 그대로 DB에 도달하고, 새로고침·뒤로가기마다 중복 기록된다.

- **퀴즈 완료 시점에 1회만** 전송
- `sessionStorage` 로 중복 차단
- **fire-and-forget** — 응답을 기다리지 않는다. 실패해도 결과 화면에 영향 없음

## 5. 백엔드 설계

> **`category_slug` 선반영 원칙**: 카테고리 확장이 목표이므로 카테고리 종속 테이블에는 지금부터 이 컬럼을 넣는다. 비용은 컬럼 하나, 이득은 나중에 **마이그레이션 없이 행 추가만으로** 새 카테고리를 여는 것. MVP 값은 전부 `'football'`.

### 5.1 `team_results` — 하이브리드 한 테이블

```sql
CREATE TABLE team_results (
  -- ── API 동기화 영역 (배치가 건드림) ─────────────────
  slug             VARCHAR(32) PRIMARY KEY,   -- 'man-city' (프론트와의 계약 키)
  category_slug    VARCHAR(32) NOT NULL,
  external_id      VARCHAR(16) NOT NULL,      -- TheSportsDB idTeam
  api_football_id  VARCHAR(16),               -- 다른 API로 가는 다리
  name_en          VARCHAR(64),
  short_code       CHAR(3),                   -- 'MCI'
  founded_year     SMALLINT,
  stadium          VARCHAR(64),
  stadium_capacity INT,
  location         VARCHAR(64),
  country          VARCHAR(32),
  league_name      VARCHAR(64),
  color1           CHAR(7),
  color2           CHAR(7),
  color3           CHAR(7),
  badge_path       VARCHAR(128),              -- '/badges/man-city.png' (우리 자산)
  instagram        VARCHAR(128),
  synced_at        DATETIME,

  -- ── 수동 큐레이션 영역 (배치가 절대 안 건드림) ───────
  name_ko          VARCHAR(32) NOT NULL,
  nickname_ko      VARCHAR(32),
  location_ko      VARCHAR(32),
  catchphrase      VARCHAR(64),
  description      VARCHAR(500),
  manager          VARCHAR(32),
  manager_note     VARCHAR(48),
  star_player      VARCHAR(32),               -- 현 소속 필수 · 이적시장마다 점검
  star_player_note VARCHAR(48),
  legend           VARCHAR(32),               -- 구단 역사 · 갱신 불필요
  legend_note      VARCHAR(64),               -- 검증 가능한 기록 근거 필수
  curated_at       DATETIME                   -- manager·star_player 기준일
);
```

**⚠️ 한 테이블로 합친 대가 — 배치에 규율이 필요하다.** 동기화 Service는 **메서드 하나로 좁히고, 기존 엔티티를 로드해 API 영역 setter만 호출**할 것. 새 엔티티를 만들어 `save()` 하면 **수동 큐레이션 컬럼이 전부 날아간다.** 미러링 패턴의 1번 사고다.

**`synced_at` / `curated_at` 분리 이유**: 자동/수동 데이터의 신선도를 따로 판단해야 화면에 정확한 기준일을 표기하고 오래된 섹션만 숨길 수 있다.

### 5.2 `participant_logs`

```sql
CREATE TABLE participant_logs (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  category_slug VARCHAR(32) NOT NULL,
  result_slug   VARCHAR(32) NOT NULL,
  created_at    DATETIME    NOT NULL,
  INDEX idx_cat_slug (category_slug, result_slug),
  INDEX idx_created (created_at)
);
```

**⚠️ 참여자 수를 매 요청 `COUNT(*)` 하지 말 것.** 바이럴로 수십만 행이 쌓이면 체감된다. → **1분 TTL 캐시**(`@Cacheable`). 1분 늦게 갱신돼도 문제없다.

이 테이블 하나가 나중에 허브의 팀 순위도 만든다 ([FUTURE §2](FUTURE.md)).

| 메서드 | 경로 | 용도 | 호출 주체 | CORS |
|---|---|---|---|---|
| GET | `/results` | **15팀 일괄** (빌드/ISR용) | Next 서버 | 불필요 |
| GET | `/results/{slug}` | 단건 (필요 시) | Next 서버 | 불필요 |
| GET | `/participants/count` | 참여자 수 (1분 캐시) | **브라우저** | 필요 |
| POST | `/participants` | 참여 기록 (완료 시 1회) | **브라우저** | 필요 |

**`GET /results/slugs` 는 만들지 않는다** — `generateStaticParams` 가 `lib/clubs.ts` 를 쓰므로 불필요하고, 빌드-백엔드 결합만 늘어난다.

**`/results` 를 일괄 조회로 둔 이유**: 빌드 시 15번 호출할 이유가 없다. 15행뿐.

**CORS**: 브라우저에서 직접 부르는 엔드포인트만 설정.

**갱신 실패 시 기존 값을 덮어쓰지 말 것.** 팀 단위 부분 성공 허용.

### 7.2 신선도 방어 (수동 데이터)

수동 데이터의 최대 위험은 **방치**. 팬 사용자는 틀린 정보를 즉시 알아채고, **사실 오류 하나가 채점 알고리즘 신뢰까지 무너뜨린다.**

1. **기준일 표기** — "감독·스타는 2026년 8월 기준". 낡아도 정직하면 신뢰가 유지된다
2. **오래되면 숨김** — `curated_at` 이 6개월 초과 시 감독·스타 섹션 미표시. **레전드는 항상 표시**하므로 인물 영역이 비지 않는다
3. **댓글이 제보 창구** — 팬이 "감독 바뀌었어요"를 알려준다

```
당신과 가장 닮은 팀은  ⟶  맨체스터 시티

감독     엔초 마레스카     펩의 제자, 점유율 축구 계승자
스타     엘링 홀란         한 시즌 36골 괴물 골잡이
레전드   세르히오 아구에로  구단 최다 득점 260골
                            감독·스타는 2026년 8월 기준
```

### 7.3 이미지 자산

- 배지 URL에 타임스탬프가 박혀 있어 저쪽이 갱신하면 **링크가 깨진다** → **파일을 받아 `public/badges/{slug}.png` 로 보관**
- hotlink 금지 (상대 서버 부담 + Next 이미지 최적화 불가)
- **선수 사진은 넣지 않는다** (초상권)
- 출처 표기 푸터 필요 (TheSportsDB 이미지는 "Most are fan created", 라이선스 불명확)

### 7.4 색상 사용 주의

`color2` 가 `#FFFFFF` 인 팀이 다수(첼시·레알·토트넘 등). 흰 배경에 그대로 쓰면 보이지 않는다. → **대비 검사 후 테두리 추가 또는 배경 반전.**

팀 색은 **표시 전용**이며 매칭에는 쓰지 않는다. `lib/clubs.ts` 가 아니라 DB/표시 층에 둔다.

### 7.5 한국어 표기 규칙

**원칙: 한국 축구 매체가 정식 기사에서 쓰는 이름.** 국립국어원 표기법(아궤로·판데이크)이나 원어 발음 근접보다 우선한다 — 사용자가 **검색해본 적 있는 이름**이어야 알아보기 때문. 개별 정확성보다 **15장 카드 전체의 일관성**이 중요하다.

#### 팀명 — 이름은 한 곳에만

- **약칭 필드는 만들지 않는다.** 필요해지면 그때 추가한다. 미리 만들면 "같은 것에 이름 둘" 문제가 다시 생긴다 (실제로 `아스날`/`아스널` 어긋남이 그렇게 발생했다)

## 8. UI 방침

**모바일 우선.** 바이럴 트래픽은 거의 전부 모바일이고 공유도 카톡에서 일어난다. 데스크톱은 중앙 정렬된 모바일 폭(`max-w-md` 수준)으로 충분하다. 참고: **푸망 · 방구석연구소**.

**다크모드 미지원** (MVP 한정).
⚠️ **"안 만들면 되는" 게 아니다.** Tailwind v4 는 OS 설정(`prefers-color-scheme`)을 따라가므로 다크모드 사용자에게 **색이 반쯤 뒤집힌 화면**이 나올 수 있다. **라이트 고정을 명시**해야 의도대로 보인다.

**공유**

| | 하는 일 | 시점 |
|---|---|---|
| **OG 태그** | 링크를 붙여넣으면 미리보기 카드가 뜸 | **MVP 필수** |
| **카카오 SDK** | "카카오톡으로 공유하기" **버튼** | 배포 도메인 확정 직후 |

한국 바이럴은 카톡이 거의 전부이며 **버튼 유무가 공유율을 크게 가른다** — 링크를 복사해 붙여넣는 사용자는 드물다. 카카오 개발자 콘솔에 **도메인 등록**이 선행되어야 한다.

푸망·방구석연구소의 **결과 이미지 저장**은 **동적 OG 이미지**로 상당 부분 대체된다 — 공유 카드 자체가 내 결과를 담으면 별도 저장 기능이 덜 필요하다.

### 8.1 척도 UI — 세로축 4점

**Q2~Q9 양극 척도는 세로로 배치한다.**

```
      걸어 잠근다!                         ← 위쪽 극 (headline + detail)
      실리적으로 역습을 노리며 승리를 굳힌다

              ⬤   완전히 위쪽    (큰 원)
              ●   약간 위쪽      (작은 원)
              ●   약간 아래쪽    (작은 원)
              ⬤   완전히 아래쪽  (큰 원)

      몰아친다!                            ← 아래쪽 극
      추가골을 노려 경기를 끝내버린다
```

**근거**

1. **세로가 극단 응답을 늘린다** — 양 끝 사이의 **시각적 거리가 가로에서 더 멀기** 때문. 확정 설계의 "점들을 가운데로 압축(끝이 멀면 극단적으로 느껴져 회피)" 규칙과 **같은 원리**이고, 중립을 없앤 짝수 척도의 취지와 같은 방향
2. **응답 부담이 낮다** — 응답 시간·신뢰도 기준으로 가로가 더 부담스럽다. 완주율이 생명인 서비스에서 유의미
3. **327px 폭에서 `detail` 텍스트가 산다** — 가로였다면 극당 약 120px에 4줄로 쪼개진다
4. **Q1(3지선다)과 일관된다** — Q1은 선택지가 긴 문장이라 세로 외 답이 없으므로, 9문항 내내 조작법이 같아진다

> 출처: [Extremity in horizontal and vertical Likert scale format responses](https://www.sciencedirect.com/science/article/abs/pii/S0167811620300367) · [Hu 2020](https://journals.sagepub.com/doi/abs/10.1177/0894439319834296) · [MeasuringU](https://measuringu.com/horizontal-vs-vertical-rating-scales/)

**방향 규칙**: `왼쪽=음수 / 오른쪽=양수` → **`위=음수 / 아래=양수`**. 90도 돌릴 뿐 의도(방향 고정·역채점 금지)는 그대로이며 **데이터는 안 바뀐다** (`ChoiceIndex` 0이 맨 위, 3이 맨 아래).

**안쪽 2점 라벨 — 상시 노출** (사용자 결정). 네 선택지 모두에 라벨을 표시하며 안쪽은 `Pole.word` 로 `약간 실리적` 형태.

> ⚠️ **기존 확정 설계를 덮는 결정이다.** 원래는 "양 끝만 라벨"이었고 근거는 *전점 라벨이 가운데를 매력적으로 만들어 극단 선택을 끌어내린다(Weijters 2010)* 였다. 라벨이 없으면 안쪽 2개가 무엇인지 알 수 없다는 판단으로 이해도를 우선했다.

- 완화 ①: 안쪽 라벨의 **시각적 위계를 낮춘다** — 작은 글씨·낮은 대비
- 완화 ②: **점 크기(큰-작은-작은-큰)와 가운데 압축**은 유지해 극단 쪽 유인을 남긴다
- 안전망: 감사가 **중앙편향 모델**(안쪽 답 2배 가중)에서도 통과 — 중앙 쏠림이 늘어도 **팀 분포가 무너지지 않음이 검증됨**
